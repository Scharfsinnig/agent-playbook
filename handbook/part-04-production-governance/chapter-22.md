# 第 22 章　成本、延迟和模型路由：把经济约束写进下一步决策

## 22.1 令每一次行动有完整价格

Token 只是成本的一部分。一次可验收任务的单位成本应至少归集模型输入/输出/缓存、编排与存储、检索与外部 API、网络与沙箱、观测与评测、人工审批/返工和失败事件的期望损失；同时同业务结果关联。否则系统可能通过降低模型价格掩盖工具调用翻倍、人工复核淹没或尾部延迟上升。更有用的指标是 `cost per safe accepted task`，并按租户、模型、工具、任务类别和版本切片，而不是全局平均 cost/token。

预算是控制面的一部分。请求、步骤、工具、子 Agent、租户、项目和周期都应有 token、费用、并发、墙钟和递归深度的硬/软额度。达到软额度可要求摘要、切换较低能力模式、异步队列或人工接管；达到硬额度必须进入明确终态，不能静默再试。OWASP 将无界消耗列为 LLM 应用风险，正是因为循环和扇出既损害财务，也能造成拒绝服务。[OWASP LLM10: Unbounded Consumption](https://genai.owasp.org/llmrisk/llm10-unbounded-consumption/)

## 22.2 路由前先收紧候选集

模型路由的第一问不应是“哪个最便宜”，而是“在这个数据、地域、风险和任务上，哪些候选被允许”。含机密资料或受特定合同约束的任务先按数据处理区域、供应商条款和已批准模型集合过滤；高后果写操作先按能力、版本和评测范围过滤；之后才以任务复杂度、上下文长度、质量预测、延迟、当前健康度和价格选择模型。低置信、冲突证据或接近行动阈值时升级更强模型或人工，而不是为了便宜绕过已测控制。

可将路由器理解为受控的分类/排序器：规则和缓存处理确定性请求，小模型完成结构化抽取、意图分类和安全前筛，主模型处理开放式综合，验证器和人处理高后果判断。Contextual bandit 可以在已经批准的候选之间探索质量—成本折中，但它不能定义任务完成、也不能让高风险动作成为实验臂。路由器本身是生产制品，必须记录 candidate set、特征摘要、选择概率/理由、模型版本、价格版本和后续结果，才能评测、回放并在非平稳环境中纠偏。

延迟优化同样不能只看单次 LLM 调用。Trace 应拆出排队、上下文构建、模型、检索、工具、审批和补偿的 P50/P95/P99，并找关键路径。只读、独立的检索可并行；有写集冲突或依赖前提的动作必须串行。缓存 key 需要包含租户、权限、数据版本和制品版本，写后失效；少一次模型调用而返回另一位客户的结果并不是优化。任何缓存、并行和降级方案都应先在安全与质量切片上证明非劣，再计算节省。

## 22.3 成本函数要参与动作选择

成本治理的错误起点是月底把账单按模型供应商相加。运行时真正需要的是动作发生前的近似总成本和动作发生后的可核对总成本。对一项任务，可按 `C = C_model + C_context + C_tool + C_runtime + C_human + C_rework + E[L_incident]` 归集：模型输入/输出/缓存属于 `C_model`；嵌入、重排、解析和上下文压缩属于 `C_context`；搜索、支付、数据库、浏览等外部 API 属于 `C_tool`；队列、状态存储、沙箱、网络和观测属于 `C_runtime`；审批、复核、升级和值班分钟属于 `C_human`；补偿、客户联络和重新办理属于 `C_rework`。最后一项是按照动作范围和历史事件估算的风险损失，它提醒经营决策不要把事故从账本中删除，但绝不能把 P0 外泄或未授权写入折算成“付得起就可以”。硬安全门仍先于效用函数。

有了这个函数，路由比较的是增量净价值而非 token 单价：`E[V(a)] - E[C(a)] - λE[R(a)]`，并且所有候选先过身份、地区、合同、数据与策略过滤。强模型若减少两轮人工复核、一次昂贵工具调用或一次高概率返工，可能比便宜模型更省；反之，低价模型造成的无效重试会在尾部成本上放大。概率应来自保留集、近期线上样本和同类任务分布，不应采纳模型自己的“信心”。每个 run 还要记录费率来源和 `price_version`，因为模型价格、缓存折扣、工具报价和人审成本会变化。运营报表至少按任务类型、风险、模型、工具、租户、路由版本和终态拆分，并同时报告安全验收任务、返工任务和被策略阻止任务的成本。

## 22.4 预算贯穿十三步，而非只在最后结算

接收请求时，系统按租户、套餐、风险和服务等级分配总额及验证/补偿保留额；建立任务契约时把检索、计划、执行、人工和恢复的额度写入状态，防止前几轮搜索吞掉验证资源。风险分级提高验证和人工的最低保留额。编译上下文前先估算解析、重排和 token 价格，超额时选择结构化摘要、缩小范围或请求澄清，而不是截掉关键证据让模型猜。形成计划后，价值—成本模块淘汰同样需要审批却多调用数个付费工具的劣势路线；子 Agent 接受父任务的预算和 deadline，不能靠扇出绕过限制。

选择下一动作时同时比较余额、剩余时间、当前不确定性、重试次数和副作用风险。继续的价值上界不足以覆盖必要验证时，`ASK_HUMAN`、`PAUSE` 或 `STOP_BLOCKED` 才是正确选择。执行前门控检查最坏情形费用、并发占用、工具配额和补偿预留；执行后按实际 usage 结算并更新估算器。观察阶段不能为了省钱跳过关键验证：没有预算完成验证时，终态必须是未验证的降级或人工接管。软额度可触发摘要、排队、经评测的低成本候选或缩小任务；硬额度触发熔断并留下未完成子目标和原因。这样，成本限制是状态机的一部分，而不是隐藏的失败。

## 22.5 并行、缓存和批处理的收益与失效

并行只在缩短关键路径、读写集不冲突、外部配额充足且结果可独立合并时有益。两个只读检索可并行；“锁座”与“确认退款”存在前提关系，即使并行更快也会破坏事务。调度器据 DAG、读写集、限流桶和补偿边界决定扇出宽度，并让取消信号向子任务传播。常见反例是让五个同质 Agent 概括同一网页：成本上升、证据仍高度相关，最后还要人工解决同一事实冲突。

缓存必须把主体、租户、权限、目的、数据版本、制品版本和时间纳入 key。公开、版本稳定的语料 embedding 可以长 TTL；库存、余额、订单和权限决定必须短 TTL 或写后失效。对敏感或高后果响应，跨主体语义缓存默认关闭；少一次模型调用却向另一客户返回信息不是优化。批处理适合离线评测、embedding、文档抽取等相互独立且可容忍等待的工作；按区域、租户、风险和重试语义分片，避免一次失败或数据边界问题影响整批业务请求。

验证指标除 P50/P95/P99 外，还应包括关键路径占比、排队年龄、扇出宽度、预算耗尽率、无效重试率、缓存命中后的错误/越权率、人工分钟、返工率、路由升级正确率和降级终态完成率。把请求限制为统一 token 数、或把批量折扣当作单位经济改善，都是反例：前者会让复杂任务反复发起，后者会掩盖用户等待和失败重跑。阈值必须由实际任务的质量—成本—风险曲线校准。

还应把成本异常看作可靠性和安全信号，而非仅是财务告警。某个工具调用次数突然上升，可能是循环、提示注入、检索污染或下游错误重试；某一租户的上下文急剧变长，可能是文件解析失控或恶意输入；人工分钟下降也可能意味着本应触发的升级被错误跳过。因此告警应关联 trace、模型/工具版本、策略拒绝、终态和质量抽检，而不是只在月末发现超支。预算模型的更新同样要经回归：把过去高成本任务简单设为“低价值”可能会系统性拒绝复杂但重要的客户请求。对低频、高后果用例，宁可保留更宽的人工和验证预算，也不要用平均历史成本压缩必要控制。

成本控制还需避免“激励错配”。若团队只以每千 token 或每任务平均费用考核，工程师会倾向压缩证据、减少人工复核、把失败任务过早标为完成，结果在投诉、返工和事件中付出更高代价。更稳妥的仪表盘把费用同完成谓词、错误副作用、人工接管结果和用户后续行为并列，并让业务 owner 参与定义哪些高价值任务允许更高预算。模型路由、缓存和批处理的任何节省，都需要在同一任务分布、相同风险约束和相近服务等级下与基线比较；否则所谓优化只是把成本转移给用户、值班人员或下游系统。

最后，预算耗尽的体验本身也是产品契约。系统应告诉用户已经完成了哪些可验证步骤、哪一项因额度或外部限流未完成、是否已转入异步队列、何时会再次尝试以及人工入口在哪里。把预算熔断伪装成模型沉默，会同时降低信任、增加重复请求，并使运营团队无法判断到底是容量不足、定价错误还是任务设计不当。

同样地，用户取消请求后，尚未发生的付费动作应被取消，已经发生但未确认的动作则进入状态查询或补偿，而不是被遗忘在队列中。这既保护预算，也保护用户对系统终态的理解。
