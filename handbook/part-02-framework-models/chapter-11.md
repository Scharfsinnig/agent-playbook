# 第 11 章　模型在执行链上的角色：它是受约束的决策组件，不是系统本身

## 11.1 先从一次模型调用看责任边界

Agent 的一次模型调用不应被理解为“系统决定了一切”。在某个状态 `s` 中，运行时把经过权限过滤的上下文、可用动作集合、预算、已知证据和当前任务契约交给模型。模型的职责是将这些输入映射为候选：可能的解释、计划片段、工具选择、结构化参数、澄清问题或停止/交接建议。运行时随后用确定性规则判断候选是否允许执行；工具层真正实施动作；验证层根据外部观察判断发生了什么。模型能提高语义决策质量，却不能取代身份、事务、金额上限、幂等、审计和完成定义。

采购变更 Agent 收到“改为 14 天”后，模型可做三件有价值的事：从自然语言中识别对象可能是供应商主数据还是某份合同条款；比较检索到的项目说明以提出受影响项目候选；把不确定性表达为“需要确认此变更是全局标准还是合同 2026-17 的例外”。但模型不应自行获得 ERP 写权限，也不能仅凭“我已修改”宣称完成。是否允许修改、修改哪个生效版本、是否需要法务或项目负责人批准，分别是策略、数据与工作流的责任。

这一划分能避免一个常见误诊：如果系统把历史合同、当前供应商记录和项目权限混杂在 prompt 中，模型会给出不稳定或越权的建议；这不证明“模型不会采购”，而是上下文编译和控制面失败。若工具 API 返回的对象 ID 不稳定，SFT 只会把旧接口的偶然模式固化。反过来，当任务状态、工具契约和验证器已稳定，模型才是可以被系统化评估和适配的部件。

## 11.2 五种模型角色及其输入、输出和失败形态

同一个基础模型可以承担多种角色，但生产设计不应把它们混成一个“万能 Agent”。角色不同，允许的上下文、评价指标和风险边界都不同。

**规划模型（planner）**

规划模型接收任务契约、状态摘要、候选动作和证据，输出计划、前置条件、澄清或交接建议。它的价值是把开放请求变成可执行的候选路径；它不授予权限，也不确认外部状态已完成。应测计划可执行率、无效分解率与重规划后的真实成功率。若任务本身可由确定性流程覆盖，或没有可靠状态与动作契约，先修工作流而不把规划失败归因给模型。

**执行模型（executor）**

执行模型在受限上下文、工具 schema 和允许动作内做语义选择、信息抽取和参数草稿，输出结构化工具调用或交付文本。它不应绕过 schema 或替代服务端校验。评价应同时覆盖工具选择、参数业务校验、端到端任务成功和错误副作用。没有稳定工具版本、验证器或权限边界时，训练执行模型只会将接口偶然性固化。

**Judge 或 critic**

Judge 接收候选结果、证据与 rubric，输出评分、缺口或不确定性，适合开放文本质量和复核候选。它不能单独认证金额、权限和真实业务状态；这些应交给确定性查询或独立回执。使用 Judge 时要测与人标/真值的一致性、位置和长度偏差，并将低置信或高后果样本交给专家。若有确定性验收器，Judge 不应成为唯一评分器。

**Embedding 与 reranker**

Embedding 或 reranker 根据查询、文档和元数据召回、排序知识、案例和记忆。它既不能判断文档已获授权，也不能判断结论为真。应在有权限文档上测 recall@k、nDCG、ACL 负向测试和答案引用蕴含率。知识更新、来源追溯和删除是这一层的典型问题；若失败来自生成器误读证据或工作流遗漏，单独调 embedding 无法解决。

**路由模型或策略**

路由组件依据任务特征、风险、预算和批准候选选择模型、检索器或升级路径，目标是在质量、成本和时延间取得可解释权衡。它不定义任务完成，也不应自由探索高后果动作。需测质量—成本 Pareto、升级正确率、最坏切片和分群下界。没有可靠短期反馈、候选集合或安全回退时，规则路由通常优于未经验证的 Bandit。

规划模型的坏计划并不总是模型能力不足。若运行时没有把“先读合同、再草拟、未经审批不得写入”的前置条件显式表达，任何优秀模型都可能先调用错误工具。因此计划的输入应含动作的读写属性、授权条件、费用、可逆性、预期证据和禁止组合，而非只给工具名称。执行模型则应被设计为在一个更窄的问题上工作，例如“对已选合同生成 `draft_change` 参数”；范围越窄，schema 与服务端验证越能接管可靠性。

Judge 的位置尤其容易被误用。它可以比较两封项目通知哪一封更清楚，或从合同段落中标出“尚未证实”的结论；但它不应替代数据库断言，也不应以一个高分抵消一次越权写入。对金额、日期、生效状态、租户隔离、引用是否存在等可确定事实，首选代码、查询、测试或独立业务回执。若必须使用 LLM-as-a-Judge，应版本化 prompt、模型、温度和 rubric，在独立人标集上校准，测量模型身份、篇幅、位置和措辞偏差；低置信和高后果样本进入人工复核。

Embedding 模型的责任同样常被误解。向量相似不是授权，也不是事实蕴含。采购 Agent 在检索前必须按主体、租户、合同生效期和文档密级过滤；召回后的文档只是证据候选。生成模型引用某段条款时，验证层还需要检查该段确实支持所作断言、版本未失效且文档未包含可执行指令。RAG 的原始论文将参数化生成器与显式非参数记忆结合，主要价值之一正是让知识可更新、可定位来源，而非保证回答自动正确。[Lewis et al., Retrieval-Augmented Generation](https://arxiv.org/abs/2005.11401)

## 11.3 一个调用如何进入受控状态机

实践中，可以把模型调用包装为一个“候选生成节点”。运行时先读取状态：任务目标、当前步骤、已证实事实、未证实假设、允许工具、预算余量、审批状态、风险等级和上次失败类型。随后构造最小上下文包：稳定系统规则置于可信指令层；文档、邮件和网页等不可信材料作为带来源标签的内容；工具说明使用 JSON Schema 或等价类型契约；输出要求写成可被解析的计划或工具调用结构。

模型给出候选后，运行时不直接执行，而是依次完成：解析与 schema 校验；检查动作是否在当前状态允许集合中；验证对象 ID、金额、日期、租户和授权票据；为写动作生成幂等键；估算预算和风险；必要时创建预览并进入审批。只有通过这些门，工具适配层才发出真实请求。工具返回必须作为原始观察记录在状态中，模型只能基于该观察判断下一步。提交 ERP 后，Agent 应以独立读接口或业务回执核验“合同 2026-17 的交付期字段已变更、变更号为 X、三个项目通知均处于待发送/已发送状态”，而不是读取自己的生成文本。

这个过程也说明模型“反思”的准确含义：当验证器报告合同版本冲突，运行时把错误代码、冲突字段和可选恢复动作加入状态，要求模型提出重规划候选。模型产生的“原因解释”只是待验证假设；例如它说“可能检索到了失效合同”，系统仍须用版本查询证实。语言反思可以帮助搜索恢复路径，但不能自动写成跨会话规则，更不能在同一轨迹中自行修改评测阈值。

## 11.4 模型角色选择的指标与反例

模型角色要用任务级指标而非通用榜单来评价。规划模型需要看计划落地前被拒绝的比例、因缺前置条件重规划的次数、每步的条件成功率和最终有效完成率。执行模型要同时看参数有效性、工具调用必要性、真实完成率和错误副作用。Judge 要看其与人标或确定性真值的相关性及最坏切片；检索要看有权限文档上的 recall@k 与答案的引用蕴含，而不是只看向量相似度。路由要看单位“安全验收任务”的成本、质量分位数与升级漏检，而不是平均 token 成本。

反例是让同一强模型同时规划、执行、评价并批准。这样做看似减少系统集成，却把同一偏差复制到全部控制点：模型选择的证据可以被模型自己的摘要掩盖，Judge 会偏好自己熟悉的语言形式，错误工具调用又被同一模型解释为“已完成”。在风险较低的问答产品中，共用模型可以是成本权衡；一旦涉及真实写入、训练数据采集或发布决策，执行面与验证/批准面必须至少在身份、权限、数据和评测资产上分离。

## 11.5 模型调用契约：让“上下文更多”变成“证据更完整”

模型调用前应有一份机器可读的调用契约。它不需要暴露全部内部 prompt，却应规定：任务和子任务 ID；调用角色；可见主体与数据 scope；允许的输入来源；上下文包中每条事实的来源/版本/时效；允许动作与禁止动作；最大 token、工具次数和延迟；要求的输出 schema；以及输出将被哪个验证器消费。这样，模型调用才可被重放、比较和审计，而不是一段无法解释的长上下文。

在采购案例中，planner 的上下文可包含合同列表、项目状态和审批规则，但不必直接带入所有附件全文；executor 只取得经 planner 和规则筛选后的合同 ID、目标字段、当前版本和 `draft_change` schema；通知生成器取得已确认的受影响项目清单，不得到 ERP 提交令牌；Judge 只看到候选通知、证据 ID 和 rubric，不拥有写工具。调用契约还要标注每一项输入是“可信规则”“权威业务记录”“外部不可信内容”还是“模型生成候选”，以免网页或附件文本被错误提升为系统指令。

这一契约改善了三种不同故障的定位。若输出 schema 不合法，是生成或解析问题；若 schema 合法但服务端拒绝，是参数、版本或授权问题；若工具成功却最终业务状态错误，是工作流或验证问题。它们各自需要不同修复，不能都作为“模型答错”投进训练。最小 trace 至少关联 run ID、模型和参数版本、prompt/模板 digest、检索文档版本、adapter、路由决策、工具请求与回执、验证器结论、审批和终态。高后果请求还应能回答“为什么该信息可见、为何该动作被允许、谁接受了风险”。
