# 第 13 章　把经验压进参数之前：SFT、LoRA/QLoRA、DPO、蒸馏、持续预训练与 RL

## 13.1 SFT：把已证明正确的条件行为变成默认行为

监督微调（Supervised Fine-Tuning，SFT）改变的是模型在给定输入条件下偏向生成什么。它最适合稳定、重复并且已有高质量示范的行为：企业术语的解释方式、固定表单抽取、受控工具调用模板、已验证的失败恢复序列，或某类标准通知的写作规范。它不适合用来存放快速变化的合同事实，也不适合修复权限、数据库一致性或不明确的完成定义。

SFT 数据不能等同于“成功日志”。一条生产轨迹可能在第七步由人工悄悄修正，也可能包含完成后才得到的回执；若把这些未来信息放进前序输入，模型会在离线评测中虚高。训练样本应以决策时刻为单位重建：当时可见的任务契约、授权上下文、工具观察、状态摘要和候选动作是什么；正确行动是什么；是否有人介入；最终环境验收为何可信。样本还应带数据用途、来源、许可/同意、客户和文档族、工具/模型版本、难度、敏感等级、评审状态与删除血缘。

实施先从窄任务开始。以采购变更为例，可先只训练“在合同条款冲突时生成包含证据、风险与澄清问题的草稿”，不训练真实提交。按时间、客户、合同族而非随机行切分数据，剔除近重复；以 prompt/RAG/工具工程为基线；逐步增加数据观察学习曲线；在固定集、时间外集、模板扰动集、旧能力集和安全集上比较。只有增益稳定、置信区间可接受且成本/维护收益成立时再扩大范围。

训练样本还应区分“动作标签”与“解释标签”。动作标签回答当前状态下可执行什么，例如选择 `request_clarification`；解释标签说明为何该动作合理，例如引用两个冲突版本。前者能被环境和策略校验，通常更适合直接学习；后者若未经证据约束，容易把事后故事或标注者风格当成因果规则。对高风险工具，保留结构化的前置条件、证据 ID、拒绝理由代码和人工接管标记，比要求模型写长篇思维过程更可审计，也更利于在工具和业务规则改变后更新。

SFT 的典型反例是把模型自生成的“成功”轨迹直接当金标。模型可能因为同一错误 verifier 获得高分，也可能在样本中用冗长解释掩盖未执行动作。应先由程序验收、独立回执或人工复核筛选；正确拒绝和人工纠正可在核验后成为正向样本，而高信息量失败默认只用于错误分类、红队或恢复样本。只有在同一决策时刻的可见信息集下补齐经验证的正确后续动作，失败轨迹才能转成 SFT 正样本。SFT 后要测 out-of-distribution 成功、模板敏感性、工具副作用、长度/成本变化和旧任务退化；训练 loss 下降只是拟合信号，不是发布证据。

## 13.2 LoRA 与 QLoRA：降低更新成本，不降低证明义务

参数高效微调（PEFT）中最常见的 LoRA（Low-Rank Adaptation）冻结基座权重，在部分层引入低秩可训练增量。它的工程吸引力是可为不同领域或租户挂载独立 adapter，训练和存储成本较低，且可更快回滚。LoRA 原始论文报告其在若干模型和任务上可接近或超过全量微调，并避免额外推理延迟，但这不表示每个业务任务都应优先 LoRA。[Hu et al., LoRA](https://arxiv.org/abs/2106.09685)

QLoRA 不是另一种 adapter 语义，而是在量化冻结基座上训练 LoRA adapter 的训练方案。其 4-bit 量化、NF4、双重量化和 paged optimizer 旨在降低显存占用；论文展示了在单张 48GB GPU 上微调 65B 模型的可行性。[Dettmers et al., QLoRA](https://arxiv.org/abs/2305.14314) 因此，注册“QLoRA adapter”时不能只保存 adapter 文件：必须固定基座权重/许可证、量化配置、tokenizer、推理内核、模板、训练代码与数据版本。否则同一个 adapter 在不同量化或 tokenizer 上的行为并非已验证行为，也谈不上可靠回退。

采购 Agent 若需要在不同业务线使用不同通知风格或稳定的条款抽取规则，独立 LoRA 可以是合理隔离方式。然而“每个客户一个 adapter”会带来路由错误、版本爆炸和组合干扰。多个低秩增量同时挂载的效果不是其单独分数的线性和；merge 到基座后还可能改变以前的输出。生产上应让 adapter registry 记录适用域、基础版本、训练数据边界、评测报告、风险 owner 和撤销开关；先通过规则或已验证 router 选择单个 adapter，只有在显式组合评测通过后才允许融合。安全关键能力下降、训练 run 方差过大、量化导致数值异常或部署内核变化时，省显存不应压过稳定性。

## 13.3 偏好优化：DPO 学的是偏好分布，不是业务真值

有些任务不存在唯一正确文字，但确实存在“两个可行结果中哪一个更符合业务偏好”的问题，例如项目通知应简洁、明确风险、不过度承诺，并给出下一步。此时可以收集 chosen/rejected 对。直接偏好优化（Direct Preference Optimization，DPO）把偏好目标重写为分类式损失，避免传统 RLHF 中先训练显式奖励模型、再用 PPO 采样优化的复杂链条。[Rafailov et al., DPO](https://arxiv.org/abs/2305.18290)

这一简化不改变监督的本质：DPO 在给定的偏好对上、以参考策略为锚进行优化，实际偏离程度由 β、数据分布和训练过程共同决定；它不能证明条款事实正确、工具已成功执行或长期业务结果变好。若标注者系统性偏好更长、更自信或更迎合的文本，DPO 会放大这种偏差；若 chosen 与 rejected 都引用了失效合同，优化只会更稳定地选择其中一种错误。实施时应先定义与任务价值相连的 rubric，例如“事实均有证据、明确不确定性、不给未批准承诺、下一步可执行”；随机交换候选位置，长度匹配或将长度作为切片；通过多人校准、仲裁和结果证据检验偏好质量。

训练后必须同时报告偏好胜率、事实/引用验证、拒绝与帮助性的 Pareto、输出长度、相对参考策略的偏离、不同客户/语言切片和真实任务结果。若任务有唯一可验证终态，如合同字段是否正确写入，则应优先使用确定性 verifier 生成或筛选 SFT 数据；若仍需要策略优化，再在该 verifier 定义的可控环境中采用 RLVR，而不是把“看起来更好”的偏好当奖励。InstructGPT 的公开流程从示范、排序到奖励模型和 RL，说明人类偏好能显著调整模型行为；其论文结果仍局限于所用 prompt 分布和人评条件，不能替代本业务的验证。[Ouyang et al., InstructGPT](https://arxiv.org/abs/2203.02155)

## 13.4 蒸馏：压缩教师行为时，要保留失败边界和回退路径

蒸馏的动机通常不是“让学生更聪明”，而是把昂贵教师在一个清晰任务域内可观察到的行为压缩到更小、更快、更私有的模型。可蒸馏的对象包括软概率、最终答案、结构化决策、工具轨迹、检索选择与何时升级的判断。经典知识蒸馏利用教师软目标保留类别间结构信息。[Hinton, Vinyals and Dean](https://arxiv.org/abs/1503.02531)

对 Agent 而言，只蒸馏最终文本常会丢失最关键的“何时查询、何时澄清、何时停止、如何恢复”。采购 Agent 的学生模型若只学会写优美通知，却没学到“合同版本冲突时交接”，会在低成本路径上扩大风险。因此训练集需要含正确执行、正确拒绝、失败恢复、长尾异常和强模型升级样例。教师输出只是候选标注，必须经 verifier、工具回放或人工抽样过滤；不能将不允许暴露的隐藏推理、私人数据或第三方版权内容直接复制进学生数据。

发布策略应是学生处理覆盖良好的低风险切片，强教师保留为不确定性或高风险回退。指标不仅比较平均质量与成本，还要比较尾部任务、越权/拒绝行为、升级漏检、不同工具版本和 OOD 差距。若学生在常规项目通知上足够好但在跨合同冲突上不可靠，正确的系统设计是路由升级，而不是用总体平均分掩盖长尾损失。

蒸馏也要防止“教师泄漏式优势”。教师可能调用了学生在生产中不可用的检索器、拥有更长上下文、得到隐藏人工提示，或用较高 test-time compute 才达到某个结果。训练卡必须说明教师可见信息和推理预算；学生评测要在自身真实工具、上下文和预算下进行。否则蒸馏报表会将基础设施差异误写成模型能力迁移，部署后学生无法复现教师轨迹。

## 13.5 持续预训练与全参更新：针对领域表示缺口，而非最新知识

持续预训练（continued pre-training）以大规模原始领域语料继续优化语言建模目标，可能改善术语、文体、代码或专业语义表征。它需要的证据比 SFT 更强：检索、prompt、工具和小规模 SFT 已不能解决稳定的领域表示缺口；语料具有明确许可、质量、去重、时间边界和足够规模；组织能承担全模型回归、供应链登记、删除/退出和长期维护。它不应成为更新政策、合同事实或人员信息的主要手段，因为权重难定位、难删除、易过期，也无法按查询主体执行权限过滤。

全参更新会增大遗忘和不可逆回归风险。可先用 PEFT、混合旧域 replay、基座行为锚定或部分冻结来限制漂移，并建立“能力 × 风险 × 人群/租户 × 时间”回归矩阵。采购领域语料提升条款理解并不意味着通用工具调用、拒绝边界或多语言通知保持不变。只有当时间外领域提升、旧能力与安全护栏都通过、且 shadow/canary 显示净收益时，才允许扩大影响面。

## 13.6 训练运行的最小可复现实验

无论选择 SFT、LoRA、DPO 还是 RL，训练作业都应先写成一个可拒绝的实验提案，而非“尝试调一调”。提案列出目标失败簇、业务和安全假设、基线版本、训练/验证/审计数据切分、可接受的改进、不可接受的退化、停止条件、资源预算与负责人。随后锁定数据快照和去重规则，运行小规模试验，检查训练损失、梯度/数值异常、样本泄漏和输出长度；再做多随机种子复现。若小规模实验只在开发集提升，或不同种子方向不一致，先调查数据和评价，而不是扩大 GPU 预算。

候选模型完成后，评测应按“模型组件—单步工具—端到端轨迹—安全故障—在线业务”分层进行。组件层可测抽取和分类；单步层测调用、参数与停止建议；端到端层在固定环境快照中测验收谓词与等价正确路径；安全层注入越权、提示污染、陈旧证据和工具超时；线上只在前述层通过后估计增量业务结果。每一层都把空结果、正确拒绝和人工交接计入，而不是仅统计“做了某事”。这种层次让训练团队知道改动究竟提升了语义模型、工具接口适应，还是恰好匹配了一个评测模板。

## 13.7 PPO、GRPO 与 RLVR：优化的是被定义的回报，不是抽象能力

强化学习适合的不是“任务有多步”这一点，而是存在可审计、难被投机的回报或验证器，并且通过策略采样能够带来超过搜索、提示或 SFT 的增益。PPO（Proximal Policy Optimization）以相对旧策略的裁剪代理目标限制更新，通常结合 on-policy rollout 与价值函数/critic；在 LLM-RLHF 中还常额外加入相对 SFT/reference model 的 KL 约束。[Schulman et al., PPO](https://arxiv.org/abs/1707.06347) 它有能力直接优化长程回报，也因采样昂贵、奖励错配、值函数不稳和分布快速变化而需要更严格的基础设施。

在代码、数学、SQL、表单和可执行工作流中，RL with Verifiable Rewards（RLVR）常比主观奖励更具产业可行性。采购 Agent 的候选轨迹可在隔离 ERP sandbox 中检查：是否只产生草稿、审批令牌是否匹配、字段是否符合生效合同、写后读取是否一致、通知是否仅发给允许对象。这里的 reward 应来自这些可审计的外部谓词；权限、不可逆动作、预算和敏感数据最好先作为可行域约束阻断，而不是写成可以被高业务分抵消的软惩罚。

GRPO（Group Relative Policy Optimization）对同一问题采样一组输出，根据组内相对回报构造优势，原始 DeepSeekMath 将它描述为 PPO 的变体并强调降低 critic 的内存成本。[DeepSeekMath](https://arxiv.org/abs/2402.03300) 它不等于“无需奖励模型/验证器的免费 RL”：组内奖励仍必须可信，reference/KL 约束、采样温度、长度和格式分布仍要监控。当一组样本全部正确或全部错误时，相对优势接近零，学习信号会变弱；当 verifier 有漏洞时，组内排序只会更高效地放大漏洞。适用任务应报告 group reward variance、有效样本率、pass@1/pass@k、长度和真实隐藏 verifier 成功，而不能只报训练 reward。

RL 的实现顺序应从安全环境开始：定义不可协商的 hard constraints；为每步记录状态、动作、工具观察、版本和 reward 分量；保留策略看不到的隐藏测试；以 SFT/搜索/规则基线比较；在多随机种子下监控 KL、熵、value loss、真实成功与奖励—成功背离；再从离线 replay 到 shadow、低风险 canary。真实线上探索并非前提。若没有可交互环境，可做保守离线学习；若只有高后果真实环境，则不应自由探索，应限于模拟器、sandbox、已批准的可逆候选或人工审批。DeepSeek-R1-Zero 没有以 SFT 作为预备阶段，但它仍使用了 RL 和明确奖励信号；“无 SFT 冷启动”不能被误称为无目标的无监督学习。[DeepSeek-R1](https://arxiv.org/abs/2501.12948)
