# 第 28 章　产业架构评审方法：用闭环定位系统缺口

架构评审不是给“Agent 成熟度”打一个平均分。应从一条真实任务开始，沿十三步逐一问：入口是否识别主体与用途；契约是否可验收；风险是否把动作分级；状态是否能恢复；上下文是否有来源、时效和 ACL；计划是否把确定性流程同模型判断分开；候选动作是否被预算和策略过滤；写入是否绑定身份、审批、幂等和补偿；环境回执是否被独立验证；失败后状态是否有合法去处；交付是否诚实呈现未决项；经验是否经过学习门。

随后按“暴露度 × 后果 × 控制缺口 × 不可逆性”排序，而不是被最炫目的模型问题吸引。若 Agent 会错误总结一篇公开文档，影响可低且可逆；若它可能以共享凭证退款、发送秘密或修改生产代码，即使发生率低也应优先处理。评审证据要可检查：用例台账、任务契约、权限图、工具契约、数据流与来源、威胁模型、评测原始结果、版本 manifest、trace/replay 样本、SLO/error budget、停止/回退演练、供应商与合规结论、豁免及到期日。没有证据的 P0 不扩大自治；P1 必须有 owner、期限、降级和复审。

评审中常见的误判有三类。第一，把模型能力当系统能力：模型能写 SQL 不代表被授权查询，模型会自评不代表结果已验证。第二，把一次 demo 当作稳定性：单次成功掩盖长链随机性、限流、状态竞争和成本尾部。第三，把合规或安全当文档末尾的复选框：真实的控制应该出现在身份、数据、工具、日志、发布和下线接口中。若任何一层只能靠人“记得小心”，它尚未成为生产控制。

最终的评审决议应给出允许的自治范围、最大租户/流量/动作、已批准模型与工具、自动回退阈值、人工接管条件、剩余风险、豁免、复审时间和签字人。一个好的决议也会明确“不做什么”：不让未评测的新模型处理敏感数据，不让长期记忆吸收未验证网页，不让 shadow 的成功取代写入演练，不让合规术语掩盖适用范围。这样，架构评审不再是阻塞创新的文书，而是把有限的探索放进可撤销、可学习和可证明的边界中。

## 28.1 一次评审会议从可重放 trace 开始

会前选择一条代表成功 trace、一条失败或人工接管 trace 和一条对抗/边界 trace。工程 owner 脱敏并冻结任务契约、初始业务状态、制品 manifest、工具回执、审批、成本/延迟和最终结果；业务 owner 标注真实价值与损失，安全 owner 选定要验证的 source—sink。没有生产 trace 时，在隔离 harness 中生成同等完整的试验 trace，并明确其与现实世界差异。

会议先重演 1—4 步：请求主体和用途、完成/禁止动作、风险分级、业务真相与执行状态是否分离；再审 5—7 步：上下文 ACL/来源/时效、计划中确定性工作流与模型候选的边界、stop/ask/handoff 是否真实可选；随后审 8—10 步：权限、审批、参数、幂等、预算如何在调用前生效，工具回执如何进入状态，验证器是否独立；最后审 11—13 步：超时、冲突、取消、供应商故障去往何种终态，交付是否披露不确定性，哪些数据能进入记忆、评测或训练。沿 trace 而非架构图审查，讨论会回到可观察事实。

业务、工程、平台/SRE、安全、隐私/法务和审批代表分别主持相应段落。记录员将每项结论标为有证据通过、缺证据、设计缺口、实施缺口、观测缺口或不适用，杜绝“感觉没问题”。

## 28.2 150 问是索引，不是平均分

150 问用于防遗漏和归因，不应用低风险的几十个已完成抵消一项 P0 外泄、错误支付或无停止能力。评审组先按闭环选出当前用例最相关的十到二十个 P0/P1，再以暴露度、后果、控制缺口、不可逆性和证据质量排序。客服写操作优先参数约束、幂等、部分失败、身份、过度代理、SLO、停止和证据链；研究 Agent 更重检索授权、新鲜度、冲突知识、引用忠实、结果评测和在线漂移。其他问题在引入新工具、记忆、模型或地区变化时再触发。

每个缺口的整改必须写出首个错误状态/span、问题编号、控制目标、实施 owner、证据形式、短期补偿、最大暴露、截止日和验证方式。例如“改签超时可能重复提交”的整改不是“加强重试”，而是持久化 transaction ID 与幂等键、超时先查询、写后读、模拟响应丢失并证明无重复副作用。复审重新运行同一失败 trace、相邻变体和红队/回归集，再以 shadow/canary 验证线上一致性。发布决议写明自治动作、批准模型/工具/区域、最大租户和预算、自动停止、人工接管、回滚、遗留风险和复审触发；未通过就明确只能处在 shadow、只读或人工辅助状态。

## 28.3 评审证据的质量决定决议的质量

评审材料常见的失败不是缺一张表，而是证据不可比较。离线评测若没有数据集、环境、工具版本和评分器版本，就无法证明候选优于基线；trace 若缺少主体、策略决定或业务 transaction ID，就无法说明一次成功是否合规；成本报表若把人工返工和工具费用排除，就会偏向表面便宜的路线。会前应指定每份证据的生成时间、覆盖范围、制品版本、已知盲点和责任人，并把“证据过期”同“没有证据”一样作为缺口处理。对高后果用例，建议至少有独立的验证者或审查者，而不是让实施同一功能的 Agent/团队自行宣布安全。

风险排序后还要识别共同根因。若十个问题都源于“工具调用没有用户身份”，优先修身份委托和网关，远比为每个工具加一条 prompt 有价值；若结果、轨迹和 SLO 都缺完成谓词，应先修任务契约与业务验收，再谈 judge 调优。评审组可以将整改分为阻断发布的 P0、限制自治范围的 P1、可排期优化的 P2，并为每项选择最小有效控制。此处的“最小”不是控制少，而是刚好在模型外封住风险：高风险写入的最小控制可能是 capability token、参数化 API、审批绑定、幂等和写后验证的组合。

发布后的复审也应预先写进决议。触发器包括模型或索引版本变化、工具 schema/权限变化、供应商地区或条款变化、数据类别变化、错误预算耗尽、出现新的攻击路径、用户投诉或法规更新。触发时系统先冻结扩大自治，再重跑相关核心集和红队集；若结果不确定，保留人工/只读降级而不是为了维持指标继续放量。这样，150 问变成连接设计、运行、事故和学习的索引：事故定位到首个错误 span 后能补一个回归；新法规或供应商变化能定位到受影响问题与台账；每次整改都能证明它减少了哪一种可观察的失败。

会议结束不等于评审结束。记录员应在短周期内将结论转成可执行工作项和证据请求，主持人检查 P0 是否已被真正关闭而非仅被解释，业务 owner 确认受限自治仍符合运营目标，平台 owner 确认可停止/回退，安全与隐私 owner 确认新增数据或工具未越出结论。下一次复审读取的是上次决议、整改证据和新的 trace，而非重新从需求文档开始。这个节奏让架构评审成为控制反馈环：每一轮都以真实运行和失败更新问题优先级，同时防止未验证的“改进”直接进入生产。
