# 第 27 章　90 天落地路线与十二个月成熟度建设

## 27.1 前九十天：先缩小风险，再扩大能力

第一个月不应从微调或多 Agent 开始，而应选一个有明确完成谓词、低到中等副作用、稳定输入和现成业务 owner 的用例。建立用例台账、任务契约、动作分级和最小 RACI；停用共享生产密钥；把工具改造成类型化、服务端 ACL、短时凭证与幂等接口；为关键任务建立二十到五十个核心/拒绝/安全案例；实现 root trace、版本 manifest、请求/步骤/工具预算、人工接管与单能力 kill switch。此时目标不是高自治，而是能够回答“为何行动、代表谁、实际发生什么、怎样停止”。

第二个月将这些骨架变成发布链路：为模型、prompt、工具、索引和策略接入离线回归、历史 trace replay、shadow、canary 与一致 rollback；建设检索来源/ACL/TTL 和记忆 quarantine；把提示注入、外泄、越权、工具失败和资源耗尽转成红队/故障注入案例；按业务终态建立质量、安全、延迟、成本和人工接管 SLO。首个生产写操作只在绑定审批、幂等和补偿可演练的窄范围内开放。

第三个月开始形成学习闭环，但不让生产自改。线上失败先归因到契约、上下文、工具、状态、模型或治理层，再进入候选经验区；验证用途、合法基础、最小化、结果、污染和代表性后，才进入评测、记忆或离线优化。演练工具禁用、凭证吊销、供应商故障、索引/模型回退、数据外泄和人工接管；同时完成供应商、隐私和地区适用评估。退出标准是一次变更能够重复评估、有限暴露、发现退化并恢复，而不是“模型已经很聪明”。

## 27.2 十二个月：从试点平台到受治理的进化

三到六个月，将身份委托、工具网关、任务状态机、trace schema、评测 SDK、预算、沙箱、审批和制品登记做成 paved road，避免每个团队复制一套脆弱 Agent。按 M0 探索、M1 内部只读 PoC、M2 受控试点、M3 有界自治、M4 高保证生产、M5 受治理进化分级；级别反映的是可证明的控制能力，不是模型大小。M3 才允许白名单内的低后果自动写；M4 需要独立验证、职责分离、强隔离、法律适用结论和停止/取证演练；M5 仅允许系统提出经隔离验证的优化候选，不能直接修改自身生产行为。

六到十二个月，组织应按季度复审技术和事故雷达：新模型、框架、MCP/供应链、法规、供应商条款、公开 benchmark 污染、线上失败簇和人工接管。将人工标签资源优先投向高影响且无法确定性验证的边界，而不是为所有输出追求昂贵标注；将模型路由、缓存和提示优化限制在批准集合内；只有在稳定、重复、可测量、且相对 prompt/RAG/工具修复确有增量的能力缺口上，才开展 SFT、PEFT 或 RL。持续进化的证明不是迭代次数，而是连续版本在独立盲测、红队、安全、单位经济和业务结果上净提升，并随时可回到已知良好版本。

## 27.3 每一阶段都有输入、产物、门禁和不该提前做的事

0—30 天的输入是一个有业务 owner 的窄用例、人工/规则基线、可访问的测试或历史工单，以及愿意共担边界的平台与安全团队。产物不是大而全平台，而是用例卡、任务契约、动作分级、数据流、工具契约、初始风险登记、20—50 个核心/拒绝/安全案例、root trace 字段、release manifest 模板和人工接管 runbook。工程 owner 交付受控流程，平台 owner 交付身份/日志/额度骨架，安全 owner 完成 source—sink 威胁建模，业务 owner 确认完成谓词和不自动化动作。门禁是所有写能力关闭或仅在模拟器中运行，敏感调用可追主体，P0 攻击被模型外控制阻断。验收证据是一条完整 trace、一次工具拒绝、一次故障后人工接管和一份风险结论。

此时不该提前做全组织知识图谱、通用多 Agent、自动微调、生产长记忆或跨业务数据飞轮；它们会放大尚未定义的权限、完成与数据边界。31—60 天的输入是已能隔离运行的第一条闭环、真实失败/拒绝样本和可观察版本变化。产物扩展为离线结果/轨迹/安全回归、历史 replay、shadow/canary、检索 ACL/来源/TTL、记忆 quarantine、工具幂等/补偿、预算账本、SLO 草案、红队矩阵和五级停止演练。产品/工程 owner 建数据集和发布流程，平台/SRE 建 replay、回滚、队列和告警，安全把攻击转自动化测试，业务定义明确降级。门禁是候选版本有基线和最大暴露，首个写操作仅在审批绑定、写后验证、幂等和补偿都演练后开放；验收看 shadow/canary 触发阈值时是否真能停止。

这时不该把 shadow 成功当成真实写入安全，也不该以几十条评测开放全量客户，更不能以“自动收集反馈”把原始 trace 送训练。61—90 天的输入是通过前两阶段的试点、明确 on-call 和足够运行证据。产物是用例/制品/供应商台账关联、例外登记、数据/地区处理结论、事故证据包、成本与质量仪表盘、供应商切换方案和线上失败回归闭环。门禁要求工具禁用、凭证吊销、模型/索引回退、异常 egress、删除和人工接管都至少演练一次；豁免有到期与撤销。验收证据是完整演练、取证查询、恢复对账和一次候选变更从离线到 canary 再回退的闭环。

## 27.4 从平台化到高保证的年度复审

三到六个月的输入是多个试点的共性失败簇和重复控制实现，输出是 paved road：统一身份委托、工具网关、状态机、trace/评测 SDK、签名/制品登记、预算与审批接口。平台委员会决定可复用能力，安全委员会验证其边界，业务委员会决定扩大哪些用例。验收看新用例接入时间、P0 覆盖、重复实现减少、回滚演练、跨租户负向测试和单位经济；平台化不是让所有团队自助开通高权限工具。

六到十二个月的输入是稳定基线、审核过的失败样本、供应商/法规变化和高保证需求，输出可以包括独立验证、多区域数据策略、供应商可迁移性、容量规划和受限制的路由优化。M4/M5 前必须具备职责分离、证据链、连续控制测试、灾备/下线演练和独立评测；没有这些，RL、自动 prompt 优化或多 Agent 只会扩大变化面。年度验收观察连续版本的安全、质量、成本净效果和复审闭环率，而不以“上线多少 Agent”作为 KPI。

路线中的度量也需要分阶段解释。前 30 天观察的是契约覆盖、敏感调用身份覆盖、P0 阻断和 trace 完整率，不能因为尚无足够流量就宣称业务 ROI；31—60 天才开始观察回归通过率、shadow—canary 差异、恢复/停止演练和单位成本的可信区间；90 天后才用接受率、返工、投诉、人工分钟和业务漏斗判断是否扩大。若某阶段指标恶化，先回到上一个已证明的自治范围，而不是用更多模型调用掩盖问题。每次阶段评审应产出继续、限制、回退或停止四种明确决议，并将未做事项同已做事项一起写入台账。
