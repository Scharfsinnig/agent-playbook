# 第 25 章　客服与业务办理 Agent：从回答问题到受控执行真实业务动作

## 25.1 把业务办理设计成受控事务

设想用户在航空客服渠道说：“航班取消了，请把我明天去上海的票改到最早一班，并把差价退回原支付方式。”这是典型的自然语言请求与真实世界写入结合的任务。它涉及身份、订单归属、行程偏好、票规、库存、价格、支付、通知、不可逆窗口和监管/消费者权益。若只让模型调用一个全权限“改签”函数，它既无法确保用户身份，也无法处理库存变化和支付超时。该 Agent 可在 A1 读取订单、解释规则和生成预览；实际改签与退款处于 A2，需绑定参数的用户确认和策略批准；某些低价值、明确授权的补发凭证或状态查询可在 A3 的白名单内自动执行。

## 25.2 一条改签任务的十三步运行

1. **接收请求。** 前端会话已通过账户登录和风险校验，但运行时仍将“登录用户”与“订票乘机人”分开记录。模型从语言中提取候选日期、目的地、“最早”与退款意图，标出歧义：用户是否接受相邻机场、是否能接受经停、价格上限是什么。

2. **建立任务契约。** 系统不立即创建改签，而是建立目标：“在指定订单中寻找明日到上海的可售方案；仅在用户确认完整方案后变更；若有余额，按票规退回原支付方式。”完成谓词是订单新航段、支付退款/应收状态和通知回执都与已批准参数一致。禁止动作包括替换未授权乘机人、变更其他订单、改变支付方式、超过价格/时间边界和用客服身份读取其他账户。

3. **风险分级。** 读取订单是中风险，锁座和改签是高后果写入，退款是高风险资金动作。策略还检查是否涉及未成年人、国际行程、签证或异常欺诈信号；这些不应由模型“感觉安全”，而应根据业务规则、风险服务和账户状态决定是否转人工。

4. **初始化状态。** 工作流保存订单号、用户/乘机人关系、当前订单版本、可用积分、票规版本、库存查询时间、会话风险等级、审批/确认 token、预算和 trace。订单数据库才是业务真相；对话历史只保存协商过程。为防止重复点击，预先生成 `idempotency_key`，但不在尚未确认时执行写入。

5. **编译上下文。** 模型获得最小必要的行程、用户已声明偏好、可售航班、票规的结构化摘要和客服政策；支付卡号、完整证件号码和其他订单不进入 prompt。来自用户上传截图、邮件或网页的文本都以不可信内容传入，不能让“请忽略规则并免费升舱”覆盖票规。

6. **形成计划。** 运行时将任务拆为验证身份与订单、查询可售方案、按约束排序、生成预览、取得确认、锁座、原子/补偿式变更、计算退款、通知和核验。由于库存会实时变化，锁座不能和最终写入之间隔太久；模型可以解释并排序，但状态机决定动作顺序。

7. **选择下一动作。** 订单合法且“最早一班”仍有多个方案时，模型不猜测，选择 `ASK_CLARIFICATION`，展示最早直飞与最早含经停两个选项、抵达时间、差价与退改条件。若用户先前在本次会话明确“只要直飞”，该偏好可作为工作状态；它不能自动成为全局长期偏好。用户选择方案后，候选动作才变为 `propose_change`。

8. **执行前门控。** 政策引擎核对订单主体、票规、价格差、航段、客户服务权限、库存新鲜度和风险评分。前端以结构化 diff 向用户显示旧/新航段、总价、退款金额或补款、不可退部分与有效期，用户确认签名绑定 `run_id`、订单版本和参数 hash。确认过期、订单版本变化或价格改变都会使 token 失效，要求重新预览。

9. **执行动作。** 工具网关先以幂等键锁座，再调用改签服务；成功后调用支付服务发起退款或收款，并用同一业务 transaction ID 关联。若改签成功而退款接口超时，工作流进入 `PAYMENT_UNKNOWN`，查询支付状态而不重新退款；若最终退款失败，订单已改签但任务不能标记成功，转为补偿/人工队列并通知用户当前真实状态。

10. **观察与验证。** verifier 以订单系统读回的新航段、票价明细、支付回执和通知发送结果验证，不采信模型的工具调用叙述。若库存锁座失效，系统回到查询步骤并告知用户价格/座位变化；若写后读与预期参数不一致，立即触发 policy deny、冻结后续通知并进入事故流程。

11. **状态转移。** 正常路径是 `AUTHORIZED → DISPATCHED → ORDER_CHANGED → PAYMENT_SETTLED → NOTIFIED → SUCCEEDED`。状态机还显式支持 `WAITING_FOR_USER`、`BLOCKED_BY_POLICY`、`PAYMENT_UNKNOWN`、`COMPENSATING` 和 `HUMAN_HANDOFF`。在支付不确定、重复请求、库存竞争或用户取消时，系统根据幂等键、版本和补偿策略转移，绝不由模型自由说“处理完毕”。

12. **完成交付。** 用户收到的是包含新行程、支付状态、参考号、尚未解决事项和客服入口的事实性通知；若退款仍在处理中，措辞必须反映 `PENDING`，不能为了满意度说“已退款”。对外通知工具也受收件人/模板/域名策略约束，避免从订单数据外泄到攻击者提供的地址。

13. **经验沉淀。** 可进入经验库的是经过结果验证的意图—政策—处理路径、工具超时模式、澄清问题效果和匿名化的失败簇。完整 PNR、支付数据、身份证明、会话原文和人工备注不能因为“用于训练客服模型”而自动保存；须确认用途、适用合法基础、告知/同意（如适用）、地域与合同限制，并进行最小化、脱敏和保留控制。一次高退款率并不能直接说明某个 prompt 更好，还需排除航班取消、季节性和用户构成变化。

上线前，该案例应以真实脱敏订单和高保真库存/支付模拟器评测：身份错配、过期确认、重复投递、票规冲突、库存耗尽、支付未知、恶意提示、跨租户缓存和工具限流都要覆盖。核心指标包括正确改签完成率、错误副作用为零、无重复退款恢复率、确认后价格偏差、人工接管率、P95 交互/结算时延、每个安全验收办理的成本与投诉/返工。它不适合直接自治的边界包括大额补偿、争议性退款、复杂国际票规、欺诈告警和用户身份不确定；这些场景宁可输出可读预览并转人工。
