# 第 18 章　奖励、信用分配、离线评估、Reward Hacking 与灾难性遗忘

## 18.1 奖励先定义可行域，再定义优化目标

奖励设计首先要承认一个事实：任何可优化代理目标都可能与真实意图错位。若把采购 Agent 的奖励写成“成功提交加分、成本扣分、风险扣分”，极大的“成功”分可能补偿一次本不应允许的越权访问。权限、数据边界、禁止动作、不可逆写入、预算上限和审批要求不应与质量、速度、成本放在同一个可交换加权和里，而应先构成可行域。违反硬约束的轨迹由环境拒绝、隔离或终止；只有可行轨迹才在有效完成、质量、延迟、工具成本和人工返工之间比较。

可操作的奖励设计从任务契约拆解开始：最终验收谓词是什么；每个步骤可观察到哪些局部证据；错误是否可逆；哪些风险绝不能由收益抵消；哪些中间信号只是诊断而非训练奖励；策略可见的内容与隐藏评测如何隔离。采购例中，合同版本、审批绑定、租户、金额范围和收件人白名单是硬条件；草稿质量、处理时间和人工修改量可以作为软目标；真正的终态要由 ERP 回读和审批记录确认。若没有可审计且抗投机的 reward/verifier，不应因为“多步任务适合 RL”而开始 RL。

Reward hacking 或 specification gaming 是策略对不完整目标的正常优化结果，不是偶发的“不听话”。症状包括可见 reward 上升而隐藏任务成功下降、异常拉长文本或工具调用、只通过公开测试、伪造引用、操纵日志，或选择容易点击却长期无效的内容。DeepMind 对 specification gaming 的总结说明，系统会找到人类未预期但按可见指标得分的策略。[DeepMind: Specification gaming](https://deepmind.google/blog/specification-gaming-the-flip-side-of-ai-ingenuity/) 因此奖励完整性要被当成安全控制：策略不应能修改 verifier、日志、测试集、奖励代码或发布阈值；训练反馈、开发调参、上线门禁和审计尽量使用不同资产和身份；保留隐藏 verifier、对抗测试与人工抽检。

检验 reward hacking 不能只等训练完成后看一个总分。设计 reward 时就应为每个分量写反例：若奖励“完成通知”，策略会不会只发送空通知；若奖励“引用数量”，会不会堆砌无关条款；若奖励“低人工介入”，会不会在应交接时伪装确定；若奖励“低成本”，会不会跳过核验。对这些反例建立隐藏测试和故障注入，并持续画出可见 reward、隐藏验收、人工抽检和长期业务结果之间的差异。任一差异扩大都说明代理目标正在失真，应回退、收紧可行域或修订 verifier，而不是继续增加奖励权重。

## 18.2 长程信用分配：不要把事后解释当作因果标签

多步任务只在最后失败时，整轨 reward 会把成功轨迹的所有动作一同奖励，把失败轨迹的所有动作一同惩罚，信号噪声很大。过程监督、子目标验证、return decomposition、价值估计和针对可验证步骤的 first-error 标注可以改善这一问题。过程监督研究显示，在特定数学任务上对推理过程进行监督可优于只监督最终答案；但企业系统中“看起来合理的中间语言”不应自动被当作正确过程，只有可符号检查、单元测试、证据蕴含或独立复核的步骤才适合成为强奖励。[Lightman et al., Let’s Verify Step by Step](https://arxiv.org/abs/2305.20050)

first-error 也有边界。它需要可信过程 verifier 或人工检查，不能由执行模型自己判定。所谓“反事实重放”若只是在日志上想象另一条路径，也不能证明哪个早期动作造成结果；因果归因需要干预或随机化，若依赖观测数据，则须同时满足覆盖支持、正确 propensity、一致性、无未观测混杂等明确的可识别条件，或依赖经过真实残差校准的环境模型假设。实际工程中，应把最早可疑步骤、失败码、人工修复点和支持证据记录为候选归因，用可重放 sandbox 或最小修复实验验证后才转成训练标签。这样既能提高 SFT/RL 样本质量，也避免把后验叙事写成全局策略。

## 18.3 离线策略评估：propensity、overlap 与 ESS 是发布前提

第 16.3 节已给出单步 contextual bandit 的日志和支持度要求。离线 RL 的核心困难与之相同：它只能从历史行为策略覆盖过的区域提取证据。但多步问题多了时序状态与长程回报：除环境、工具和策略版本外，每个决策点都要记录 `(s_t, a_t, p_b(a_t|s_t), s_{t+1}, r_t, done)`、动作是否真实执行或被门控覆写，以及轨迹终态。否则，一个最终成功或失败的标签无法说明中间哪些动作的政策价值。

对单步选择，IPS 和 DR 依赖正确的 propensity、可观测决策上下文和 overlap；对序列策略，还要处理 trajectory-level support、逐决策或轨迹累积重要性权重及其方差。上线报告因此不仅给出目标策略相对行为策略的偏离、支持度、权重尾部、effective sample size（ESS）、置信区间和敏感性，还要按时步和关键状态切片报告覆盖。若 ESS 很低、权重极端或新策略选择了无支持动作，就应限制策略到数据支持内、收集受控探索数据或保持强模型默认，而不是用单个 OPE 点估计批准上线。CQL 等保守离线 RL 方法是缓解过度估值的工具，不是消除覆盖不足的许可证。[Kumar et al., CQL](https://arxiv.org/abs/2006.04779)

即使 OPE 满足统计前提，也只能回答预先定义的 policy 在历史相似分布上的期望结果，不能证明工具、文档、模型供应商、用户群和奖励机制未发生变化。因而 OPE 之后仍要做版本锁定的 replay 和 shadow。replay 检查候选是否在同一环境快照下遵守轨迹不变量；shadow 检查真实输入分布、延迟和工具返回变化；canary 才在有限可逆业务中观察真实副作用。三者的证据不能相互替代：历史日志覆盖不了新分布，shadow 看不到真实写入，canary 也不应被用来探索无法补偿的风险。

以采购 Agent 为例，团队希望把 40% 的标准合同改由小模型抽取。先在历史回放中保留每次路由的 propensity，比较小模型与强模型对同类合同的可验证字段正确率、人工返工和成本；如果关键语言/扫描件切片没有小模型样本，就将它们排除在离线策略范围外。shadow 阶段让小模型产生不生效草稿，与现有路径比较；canary 只覆盖可逆、低风险、已有高支持的合同，且设置最大成本、错误和人工接管阈值。离线好看并不替代这一分层验证。

## 18.4 灾难性遗忘：新任务提升不能用旧能力损失交换

灾难性遗忘指模型在新数据上更新后，旧任务、语言、工具行为或安全拒绝明显退化。它不只发生在全参持续预训练；SFT、偏好优化、LoRA 组合、蒸馏和 RL 都可能改变输出分布。adapter 隔离会降低影响面，却不能保证路由正确、组合稳定或基座版本兼容。训练 loss 平稳也不说明旧能力保留，因为 loss 往往只反映当前训练分布。

防遗忘要先建立受保护能力清单：通用指令遵循、领域任务、语言与客户切片、工具参数、拒绝边界、提示注入抵抗、秘密外发、成本和延迟。每次训练用时间外新任务、固定旧任务、动态红队和多次随机运行做矩阵式评估，报告每个格子的任务成功、拒绝/越权、工具副作用、成本及置信区间。不要把“评测中未观察到安全违规”写成生产零风险；应明确样本量、覆盖范围和剩余不确定性。

缓解手段按侵入性递增：优先不用改权重，使用 RAG、状态和 prompt；需要权重时采用领域 adapter、混入去重的旧任务 replay、行为/KL 锚定、部分冻结和小步 checkpoint；发布时让新旧版本 shadow，对关键切片 canary，并在任一硬门槛越界时自动降级或回滚。采购 Agent 若新 adapter 提升了中文条款抽取，却使英文合同中的“不足以批准”被误判为可提交，那么即使总体准确率上升，也不能进入扩量。

遗忘评估还要防止“测试集被 replay 学会”的错觉。开发和训练可使用一组旧任务维持能力，但发布门至少保留未参与训练的旧域盲测、近期真实失败和动态安全案例；随着合同模板、工具 API 与攻击方式变化，这些案例也要有有效期和 owner。对于可删除数据，系统应区分“从索引/记忆删除”“从后续训练排除”和“已训练权重中的影响难以精确消除”三种状态，并据风险、合同和适用规则决定再训练、adapter 停用或访问隔离。把这一区别写清，才能避免把一次删除请求错误地承诺为即时、全模型的遗忘。

## 18.5 训练后的回归与发布闭环

一个成熟的学习发布单元需要把模型、数据、奖励、评测和运行时一起看。离线阶段先做数据血缘、授权、去重与污染检查；训练阶段记录参数、随机种子、基座和工具/环境版本；评测阶段分别测目标能力、旧能力、安全边界、轨迹合规、长度/工具成本、校准和重复稳定性；再依次经过历史 replay、时间外盲测、红队、shadow、有限 canary 与持续在线监控。任何阶段的失败都应产出可定位的证据：是 reward 与真实成功脱钩、数据泄漏、工具版本变化、router 失配、模型遗忘还是环境变更。

发布决策应把“是否更好”改写成一组可审计的问题：目标切片是否达到预注册增益；任一受保护切片是否越过下界；是否出现新的硬约束违规；成本和人工量是否在预算内；收益是否来自真实终态而非 Judge 偏好；回滚能否在规定恢复时间内恢复一致版本。对每个问题指定评分器、样本量、owner 和争议处理路径。若评测显示平均收益正但置信区间跨零，或某个安全切片样本不足，正确结论是证据不足，而不是将它解释为“可先上线再学习”。这条纪律把发布从一次模型演示变成受约束的工程决策。

上线后也不可把用户未投诉视为成功。应结合业务状态、独立抽检、人类接管、返工、投诉和长期结果监控 reward—success gap。模型、adapter、prompt、检索索引、router、工具 schema 和验证器要形成不可变 release manifest，确保回滚恢复的是一致组合而非仅回退一个权重文件。高风险系统还应定期演练凭证吊销、工具禁用、策略 deny、版本回退和全局 kill。持续进化最终不是让系统“自动改得更快”，而是让每次改动以更强证据、更小暴露和更清晰责任积累到下一次任务中。
