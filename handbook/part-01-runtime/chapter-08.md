# 第 8 章　人在回路与多 Agent：何时协同，怎样交接与仲裁

## 8.1 人在回路不是一个阻塞弹窗

人工介入应发生在系统无法合法或可靠推进的决策点：关键槽位缺失、权限升级、不可逆动作、独立证据冲突、风险超过自治信封、继续计算价值为负但任务尚未满足，或补偿需要业务判断。向人提交“请确认”而不说明对象、参数、影响、证据和替代方案，会使审批退化为橡皮图章。好的 handoff packet 是最小、可行动的状态投影：任务契约、当前状态、已验证事实、冲突/未知项、建议动作、影响范围、有效期、可撤销性和 trace 引用。

在供应商案例中，数据跨境条款触发法务审阅。运行时保存检查点并进入 `ASK_HUMAN`，而不是保持一个模型连接一直等待；法务在界面上看到相关合同片段、政策版本、模型提出的 claim 与反证、将要创建的内部工单以及批准的精确范围。回复到达后，它成为带身份和版本的事件，恢复节点从可重放状态开始执行。若审批已过期或合同版本变更，系统要求重新确认。

## 8.2 多 Agent 只解决真正独立的协作问题

当单 Agent 已有明确工具、良好验证器和足够上下文时，增加角色经常只增加通信 token、状态同步与错误相关性。多 Agent 值得的条件是：子任务可独立验收并可并行；确实需要不同权限或专业边界；需要独立证据/反方复核；或需要将长任务分割为隔离的故障域。否则，一个带清晰 Workflow 节点的单 Agent 通常更简单。AutoGen 的官方文档也建议先优化单 Agent，再在复杂任务需要多样专长与协作时组队。[AutoGen Teams](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/teams.html)

在案例中，可以并行派出“合同抽取 Agent”“公开风险检索 Agent”和“政策映射 Agent”，但它们不应共享一个可随意改写的对话历史。每个子任务要有任务引用、输入快照、允许的工具与数据域、预算、截止时间、验收谓词和输出 schema；产物应是带来源、版本和 owner 的不可变 artifact。聚合器读取这些 artifact，并在发现合同版本不一致时将冲突送入 review，而不是让最后说话的 Agent 覆盖其他结论。

## 8.3 拓扑、交接与信用分配

主控—专家结构适合统一责任和高风险动作：主控分配任务、管理预算和终态，专家只返回受限产物。DAG 适合可预先描述依赖的并行检索与汇合。handoff 适合明确所有权从一个专业角色转给另一个角色。共享黑板可服务于异步协作，但必须有字段 schema、版本和 owner。开放群聊/辩论只适用于发散和证据审阅，并且要有外部终止条件和聚合协议；仅检测文字 `TERMINATE` 不能作为高后果任务的完成依据。AutoGen 文档明确指出，未配置 termination condition 的 team 可无限运行。[AutoGen API](https://microsoft.github.io/autogen/stable/reference/python/autogen_agentchat.teams.html)

信用分配不能只看最终报告是谁写的。运行事件应形成因果 DAG：谁提供了哪项证据、哪个验证器否决了错误路径、哪个工具延迟造成阻塞。团队可以用 first-error、反事实消融或边际贡献近似分析质量和成本；Shapley 类方法有理论吸引力，却在参与者增多时成本高，且不能把观察到的相关性误写成因果真值。高影响的归因与惩罚仍需要人工审阅。

## 8.4 协作的失败机制与控制

多 Agent 常见的失败不是“某个模型说错了”，而是全体共享同一错误前提而形成虚假的共识。要降低这一风险，应让需要独立复核的 Agent 在看到他人结论前先完成盲初稿，要求每项主张携带来源，并显式分配反证角色。不同模型并不天然独立：它们可能共享训练偏差、同一检索库和同一个错误工具。2026 年关于多 Agent 多样性的研究发现，同质 Agent 扩容存在强烈边际递减，而模型、提示或工具异质性可带来互补证据；这是一项受控研究结论，不是“多加角色必更好”的承诺。[Understanding Agent Scaling via Diversity](https://arxiv.org/abs/2602.03794)

另一个失败是等待环：合同 Agent 等法务 Agent 提供规则解释，法务 Agent 又等合同 Agent 提供完整条款。运行时应维护 wait-for graph，并要求每项依赖有 owner、deadline 和 fallback；检测到环后由协调器取消或重排一个分支。并发写共享资源则不能用聊天协调，应使用第六章的锁、版本和事务控制。

## 8.5 指标、边界与案例收束

评估多 Agent 必须与强单 Agent 基线比较：相对成功率、每个安全验收任务成本、关键路径延迟、通信 token 占比、重复劳动、合并冲突、错误相关性、交接后解决率和未归属 artifact 比例。若三个 Agent 的答案高度一致但都引用同一个过期政策，投票数并不提高可信度。

在人类责任不能委托的领域，多 Agent 不能替代适当的人类决定；它们最多提供结构化证据和选项。对强耦合的单一写事务，也不应拆给独立 Agent。下一章将把单 Agent、人和团队都放进同一参考架构，展示控制面、执行面和学习面如何分工。
