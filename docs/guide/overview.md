# AI Agent 技术框架、任务执行与持续进化实践手册

> 版本：2026-08-19
>
> 定位：从 Agent 的任务执行视角，贯通框架、模型、工具、记忆、学习、评测、安全与组织治理
>
> 说明：本文讨论的是技术与工程治理方法，不构成法律意见，也不把任何单一框架、模型或算法视为通用答案。

## 写在前面：真正需要整理的不是名词，而是一条可运行、可验证的因果链

谈论 AI Agent 时，人们很容易从名词出发：先列模型，再列 RAG、Memory、Tool、Planning、Multi-Agent、SFT、LoRA、DPO 和 RL，最后补上评测与安全。这种整理方式看起来覆盖面很广，却经常无法回答工程团队最关心的问题：一个请求进入系统以后究竟发生了什么？哪一步由模型判断，哪一步由框架控制？模型为什么要看到这些上下文？工具调用失败后由谁决定重试？系统凭什么断言任务已经完成？一次失败如何进入学习系统，又怎样避免把错误经验训练回模型？

这些问题不能靠继续增加技术名词解决，因为它们缺少的是一条贯穿始终的因果主线。本手册选择从一次真实任务的生命周期出发：Agent 接收请求，先把自然语言意图编译为可执行的任务契约；随后建立状态，选择与当前决策有关的上下文，形成计划并选择动作；任何会影响外部世界的动作都要经过权限、参数、预算和风险门控；动作执行后，系统从环境取得可核验的观察，再决定继续、重试、换路、回滚、求助还是停止；任务结束后，轨迹不会自动变成“经验”，而要经过结果验证、数据治理、归因与发布门禁，才可能更新记忆、策略或模型参数。

从这条链看，Agent 不是一个会自行思考的黑盒，而是一个**以模型提供开放式判断、以运行时维护状态、以工具接触环境、以验证器确认结果、以治理系统限制后果的闭环系统**。模型能力很重要，但模型只是其中一个部件。一个更强的模型可以提高理解、规划和候选生成的质量，却不能替代数据库的事务语义、访问控制、审批绑定、幂等、审计、事故停止，也不能自行证明它产生的答案和动作正确。

这也是本手册处理“框架 + 模型”的基本方式：不把二者拆成两本互不相干的百科，而是在任务链的每一个节点说明它们怎样配合。框架负责保存哪些确定状态、限定哪些合法动作、调用哪些外部能力以及如何恢复；模型负责在确定性代码难以穷举的地方理解语义、提出候选、比较证据和做出受约束判断。二者的边界不是固定的。随着任务模式被认识、验证规则成熟，原本交给模型的部分可以逐步下沉为更便宜、更稳定的工作流；反过来，只有当环境确实开放、路径无法预先穷举且模型决策带来可测增益时，才值得提高自治程度。

## 本手册要建立的统一认识

第一，**任务完成不是一句自然语言，而是一组可验证条件**。模型说“已经处理好”只能算一个候选陈述。真正的完成需要环境状态、测试结果、业务回执、证据覆盖或授权人的确认。没有完成谓词，Agent 就不知道何时应该停；没有失败、阻塞、等待和接管等明确终态，系统就会把所有异常都误解成“再试一次”。

第二，**Agent Loop 不是一个裸露的 `while` 循环，而是受约束的状态转移系统**。每一轮都应从当前状态和新观察出发，构建本轮上下文，生成候选动作，经过策略门后执行，再把真实结果写回状态。循环能否继续，不由单一最大轮数决定，而由任务是否完成、是否取得进展、是否出现重复或振荡、继续计算的预期价值、是否被外部条件阻塞以及硬预算是否耗尽共同决定。硬上限仍然存在，但它是最后一道防止失控的安全网，不是任务逻辑本身。

第三，**上下文不等于状态，记忆也不等于聊天历史**。状态是系统在模型调用之外持有的任务事实；上下文是为了某一次判断，从规则、任务状态、知识、记忆、工具说明和历史证据中编译出来的有限输入；长期记忆则是经过来源、权限、有效期和写入门治理的跨会话资产。如果把三者混在一个不断增长的消息数组里，系统会同时遇到遗忘、污染、权限串线、成本上升和无法重放等问题。

第四，**学习不是把生产日志直接拿去微调**。一次成功轨迹可能只是运气，一次失败也可能来自工具故障、权限配置、过期知识或错误的完成定义，而不是模型参数。系统必须先定位失败发生在哪一层，再选择成本最低且责任最匹配的干预：修任务契约、改工具 schema、调整检索、增加验证器、更新提示与路由，仍然不足时才考虑 SFT、偏好优化或强化学习。所谓持续进化，是多个时间尺度的受治理更新，而不是允许线上模型不经验证地修改自己。

第五，**自治的上限由可控后果决定，而不只由模型能力决定**。当动作可逆、影响范围小、结果可快速验证时，系统可以允许更充分的自动探索；当动作涉及资金、身份、删除、公开发布、敏感数据或他人权利时，即使模型表现很好，也应把权限、审批和影响范围放在模型之外强制执行。真正成熟的 Agent 不是“什么都敢做”，而是知道什么能做、凭什么做、做错后如何止损，以及何时必须把决定交还给人。

## 如何阅读

第一篇沿一次任务从进入到结束逐步展开，适合希望先看懂 Agent “内部到底怎么跑”的读者。第二篇把这条执行链映射到参考架构和模型适配方法，回答框架与模型分别解决什么问题。第三篇讨论任务结束后的学习与持续进化，重点澄清 UCB、Bandit、无人工标注学习和强化学习的适用边界。第四篇把系统推到生产环境，讨论评测、安全、可靠性、成本与组织责任。第五篇通过三类完整案例重复同一条任务链，并给出从试点到规模化的建设路线。

附录中的 150 个问题是一套诊断索引，而不是正文的压缩替代品。遇到具体项目时，可以从问题索引定位风险，再回到对应章节理解成因、设计与验证方法；准备上线时，则使用门禁清单要求每个结论有 owner、有证据、有阈值和有回退。这样，问题库、正文和清单分别承担“发现问题”“理解并解决问题”“证明控制已经实施”三个不同角色，不再相互混杂。

## 快速导航：先按你要解决的问题读

- **想先弄清 Agent 从请求到完成到底怎样跑**：阅读第 1—7 章。这一路径会依次讲清任务契约、状态、上下文、计划、工具、验证、纠错与停止。
- **正在选框架，或分不清 SDK、状态图、持久工作流、协议和多 Agent**：阅读第 8—10 章，重点看第 9 章的责任分层和第 10 章的 Workflow/单 Agent/多 Agent 选择边界。
- **想知道模型怎样选，什么时候用 Prompt、RAG、工具修复或微调**：阅读第 11—13 章。这里不按算法热度排序，而按失败证据选择最小有效干预。
- **想做持续学习、数据飞轮、Bandit 或 RL**：阅读第 14—18 章。建议先看多时间尺度更新，再看 UCB/OPE/RL，避免把局部选择算法误当成整个 Agent 的停止和学习机制。
- **准备从原型进入生产**：阅读第 19—23 章，再用附录 B 做上线门禁。这条路径覆盖评测、权限、可恢复执行、成本、责任和下线。
- **想直接看实际任务怎样一步一步跑**：阅读第 24—26 章。三个案例分别代表证据型研究、会改变真实业务状态的办理、以及具有代码和 CI 副作用的软件工程。
- **正在制定落地计划或开架构评审会**：阅读第 27—28 章，再用附录 A 定位问题、附录 B 作决议、附录 C 统一状态和指标口径。

## 全书贯穿的任务执行链

为了让不同章节讨论的是同一个 Agent，本手册统一采用十三个阶段。它们不是要求所有实现都必须建立十三个独立服务，而是一套用于厘清责任的逻辑分解。

1. **接收请求**：系统取得用户请求、环境事件或上游工作流信号，同时保存请求主体、租户、时间、入口和原始内容。此时只知道“有人提出了什么”，还不能直接等同于已授权任务。
2. **建立任务契约**：系统澄清目标对象、交付物、验收条件、禁止动作、预算、期限与终态。缺失高影响参数时，正确动作是追问或拒绝猜测。
3. **风险分级**：系统根据数据敏感度、动作副作用、可逆性、影响对象和法规场景决定自治范围，预先标记需要审批或只能生成建议的节点。
4. **初始化状态**：运行时创建任务 ID、版本、计划、待办、证据账本、预算账本、授权状态和审计关联。业务真实状态保留在权威系统中，而不是复制进模型记忆后当作真相。
5. **编译上下文**：系统围绕本轮决策选择必要规则、最新任务状态、获准知识、相关记忆、可用工具及关键历史。上下文必须同时考虑相关性、来源、新鲜度、权限和 Token 成本。
6. **形成或更新计划**：模型或确定性规划器把目标转成可验证子目标，标出依赖、前提、产物和失效条件。稳定部分可以预先规划，受环境影响的部分采用滚动规划。
7. **选择下一动作**：系统在直接回答、检索、调用工具、请求澄清、委派、验证、重规划、回滚、等待与停止之间选择。模型可以提出动作，但动作是否可用先由候选集合和策略约束决定。
8. **执行前门控**：在任何外部动作发生前，确定性代码校验 schema、身份、资源范围、权限、预算、截止时间、审批哈希、幂等键与当前版本。未通过门控的动作不会因模型“坚持”而放行。
9. **执行动作**：工具适配层执行查询或写入，设置超时、重试分类、隔离与审计，并保留服务端返回。模型不得编造工具已经成功，也不能把网络超时简单等同于动作未发生。
10. **观察与验证**：系统解析工具结果，将事实、错误与不可信文本分开；必要时写后再读、运行测试或调用独立验证器，确认局部后置条件和整体完成谓词。
11. **状态转移**：运行时把新证据写入账本，更新计划与预算，并在继续、局部重试、换工具、重规划、补偿、降级、求助、等待或终止之间作出显式转移。
12. **完成交付**：系统提供满足契约的交付物，同时说明证据、已执行动作、未完成项和剩余风险。对高影响任务，交付还包括业务回执和可追溯审计引用。
13. **经验沉淀**：轨迹进入隔离的数据流水线。只有在结果可验证、用途允许、来源可追溯、污染风险受控且评测增益得到证明时，经验才会更新记忆、策略、提示、检索或模型参数。

后续每一种技术都会被放回这十三个阶段中讨论。读者因此可以判断：它究竟解决哪个阶段的哪个失败，依赖什么信息，引入什么新风险，以及应当用什么证据证明它确实有效。
