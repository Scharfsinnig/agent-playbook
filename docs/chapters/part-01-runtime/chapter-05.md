# 第 5 章　规划与推理：何时分解、何时搜索、何时重规划

## 5.1 计划是可检验假设，不是要被忠实执行的长篇文本

规划的价值在于把总目标分成能验证、能分配资源、能在变化时局部修复的子目标。供应商案例的一份好计划不会只写“查合同、查风险、写报告”，而应说明：先确认供应商实体与合同版本；并行读取政策与外部风险；等待制裁筛查；将每项发现映射到准入规则；若出现跨境条款例外则请求法务审阅；最后以证据清单验证交付。每个节点都需要前置条件、预期效果、验证器、拥有者、资源读写集和必要的回退/补偿信息。

一次性规划到底在静态、低风险、步骤可预测的流程中是有效的；开放环境中则更适合滚动规划。所谓滚动不是每一步推翻一切，而是在计划中显式保存假设：合同版本未变化、制裁服务可用、政策版本适用于该实体。当新观察否定某个假设，运行时只使依赖该假设的节点失效并重算，而不是让模型凭感觉重新开始。这样可降低计划漂移，也避免把旧证据带入新对象。

## 5.2 推理与验证的独立性

模型很擅长提出解释，却会把语言连贯误当作事实充分。规划系统应维护 hypothesis ledger：每个关键假设有支持证据、反证、来源、有效期、当前状态和下一验证动作。例如“供应商 A 未受制裁”不是一个可直接写进报告的结论，而是一个待验证 claim；制裁查询的时间、名单版本、实体匹配置信度和结果才是支撑它的证据。若实体匹配不唯一，正确动作是澄清或交给人，不是选择看起来最像的名称。

对于关键结论，生成者和验证者不应共享完全相同的盲点。低成本场景可先用 deterministic checks，例如 schema、日期、版本、一致性和禁止动作检查；高价值结论再使用独立来源、不同模型或人工复核。所谓“多次自我反思”若仍使用相同模型、相同上下文和相同错误证据，往往只是强化原有偏差。应要求 critic 输出可执行的反例检查或缺失证据，而不是一个没有依据的分数。

## 5.3 搜索、计算价值与 UCB 的严格位置

对于“用哪个已批准检索器、模型或提示模板”这类局部选择，Contextual Bandit、UCB 或 Thompson Sampling 可以利用任务特征和历史结果做探索—利用权衡。它们适合学习路由，在价格、延迟或成功率会变化的工具集合中选下一次试验；非平稳环境还需要滑动窗口、折扣统计和变点回退。它们不适合替代任务完成定义。

尤其需要纠正一个常见误解：UCB 会在持续交互中优先尝试估计较高或估计不充分的臂；它的理论对象是选臂与遗憾，不是“这个业务任务已经完成”。即便加入名为 `STOP` 的臂，普通累计遗憾的 UCB 也不会自动获得正确的业务停止语义。停止需要由外层策略决定：已验证完成；或继续一次计算的预期增量价值小于计算、延迟和风险成本；或触发不可恢复阻塞、预算、安全门和人工接管。若目标是“以既定置信度确认哪个方案最好”，应使用带有显式停止规则的 best-arm identification 方法，例如 Track-and-Stop，而不是把 UCB 误称为停止器。[Track-and-Stop](https://proceedings.mlr.press/v49/garivier16a.html)

计算价值（value of computation, VoC）也不是模型口头说“再想想值得”。它是比较执行当前最好行动与先做一次额外检索、模拟或评审后再执行的期望效用差，并扣除成本、时限和风险。工程上很少能精确算出该值，仍可用经过历史校准的特征近似：新增独立证据的概率、关键验收项缺口、当前模型/工具不确定性、尾延迟和动作后果。高不确定且不可逆的写操作通常应提高人工门，而不是无限增加推理 token。

## 5.4 计划执行与重规划的步骤

调研 Agent 可以先把计划编译成依赖图。只读且彼此独立的政策查询、公开风险检索可以并行；依赖实体确认的制裁查询必须等待统一实体标识；报告综合必须等待至少一项有效的每类证据。并行分支在汇合时要带输入快照和输出版本，聚合器只接受与当前主体、合同版本相一致的产物。若合同更新，旧分支可以被标为 stale，而不是被摘要悄悄混入新报告。

重规划触发器应是可观察事件：前置条件失效、工具永久失败、资源冲突、独立证据矛盾、预算不足或策略变更。重试并不等于重规划。网络瞬断可在退避后重试同一个幂等读动作；参数校验失败需要修正参数；权限拒绝应请求授权或终止；业务规则冲突则需重新读取事实与选择替代路径。把错误分类写入状态，让系统能评估“重规划是否真的降低失败”，而不是把所有失败隐藏在模型重新生成的文本中。

## 5.5 指标、边界与案例收束

应按计划节点测验收失败率、假设失效率、重规划原因、关键路径时延、分支浪费、不同验证器之间的分歧和每增加一次计算带来的成功增益。若多轮规划显著增加 token，却没有增加证据覆盖、测试通过或人工接受率，说明问题可能在工具契约、知识时效或任务定义，而非“模型推理深度不足”。

对高监管、反馈极弱或不可逆的决策，规划模型应退为建议者：它列出可能路径和待确认事实，由确定性流程及人工决定行动。对极稳定且字段明确的流程，则应把计划编译为 Workflow，而不是每次从头让模型决定。第六章把计划中的候选动作放进真实工具边界，说明为什么一次 API 调用在工程上常常是一段事务。
