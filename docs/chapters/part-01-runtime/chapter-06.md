# 第 6 章　工具调用与真实世界行动：从候选动作到可恢复事务

## 6.1 工具不是函数签名，而是带业务语义的承诺

模型看到 JSON Schema 后可以生成形状正确的参数，却不知道这个动作是否被授权、会影响什么资源、是否可逆、超时意味着什么，或重复执行会产生何种后果。工具契约因此应超出名称、描述与输入输出 schema，包含 effect（只读、追加、破坏性）、资源 scope、前后置条件、风险级别、速率和费用、超时策略、幂等性、补偿方式、数据分类、审计字段与版本。MCP 支持输入/输出 schema 以及 read-only、destructive、idempotent 等注解；这些注解有助于发现与提示，却不能由不可信工具服务器单方面成为安全授权依据。

截至 2026-08-19，应以 MCP 2026-07-28 的正式规范为时点，而不把旧版会话模型当作当前语义：stateless core 处理客户端与服务端的基础互操作，长时任务位于 extension，同时引入 MRTR、header routing 与认证加固等变化。[R06]({{ '/references/#r06' | relative_url }}) 这不改变应用架构的基本责任：协议不能替代应用自己的 run 状态、目的授权、幂等账本、事务或补偿。兼容旧版 MCP 的系统应在适配层显式维护会话/任务语义，固定协议版本并在迁移时回归测试工具发现、认证 header、长时等待和取消；不能因“客户端能调通”就推断恢复与权限语义仍然正确。

在案例中，`get_contract` 是读取型工具，`request_legal_review` 会创建内部工作项，`update_supplier_status` 是高后果写入并且被任务契约禁止。即使模型生成了后者的合法 JSON，网关也必须拒绝。反过来，一个只读工具也不必然低风险：宽范围搜索、日志导出和外部浏览可能泄露个人信息或消耗高额配额，因此同样需要目的绑定、数据分类与速率门。

## 6.2 幂等、回执与“未知结果”

写操作最危险的瞬间常发生在网络超时之后。客户端没有收到响应，可能是请求根本未到达，也可能是远端已经提交而响应丢失。把 timeout 当作失败并直接重试，可能重复下单、重复发邮件或重复创建审批。正确的协议将结果至少分成 `success`、`failure` 和 `unknown`：每个可写动作携带稳定的 idempotency key，服务端原子保存 key 与回执；同一 key 重试时返回同一逻辑结果；若结果未知，运行时优先查询状态或等待回调。

幂等不是“不会出错”，也不是自动的 exactly-once。它只是让重复提交在一个明确定义的操作域内不额外改变结果。键的作用域必须包含业务对象、动作语义与适当的期限，防止不同请求误共享键；消费事件的投递通常仍是至少一次，因而下游还需要 inbox 去重、序列号或版本比较。事件溯源与异步请求模式可用来检查重复投递和丢失响应下的处理边界。[R08]({{ '/references/#r08' | relative_url }})

## 6.3 跨系统事务与补偿

供应商准入若需要创建法务工单、锁定供应商记录、发送内部通知并写审计，多系统通常不存在一个可用的全局 ACID 事务。此时可用 saga：每个本地步骤成功后记录 forward receipt 和相应补偿；后续步骤永久失败时，协调器按业务语义执行补偿或进入人工处置。补偿不是数据库回滚的同义词。已发送的通知可以再发更正，已被其他人修改的记录不能盲目写回旧值，法律签署更可能不可逆。因此，应提前定义 pivot：在不可逆点之前完成最关键校验和审批；跨越 pivot 后不再承诺回到起点，而是保证达到一个可解释、可审计的业务终态。

补偿本身也会失败，应当幂等、可恢复，并被同一 trace 与原动作关联。补偿要根据并发工作定义业务特定的反操作，不必按原顺序执行，且必须记录进展以便失败后恢复。[R08]({{ '/references/#r08' | relative_url }}) 对无法可靠补偿的动作，系统应缩小影响范围、采用最终确认和人工门，而不是假设“有 rollback 按钮”。

## 6.4 派发、并发和等待的工程实现

工具网关可实施以下顺序：对模型候选做 schema 与语义校验；以身份、目的和资源进行授权；预留预算与并发配额；写入意图、参数哈希、工具版本与幂等键；再派发调用；接收或轮询回执后追加事件；最后由验证层判断效果。资源有并发写风险时，需要 compare-and-set、乐观版本、租约/fencing token 或按资源 key 排队。让模型管理锁顺序或猜测并发安全性是不可靠的；模型只应声明它希望读写的资源集合。

长时工具不应让 worker 阻塞地轮询。运行时应把 `WAIT` 作为持久状态，保存 job handle、correlation ID、回调验证信息、下次检查时间和 deadline；等待期间可释放 worker。回调到达时应验证签名、去重并检查 cancellation epoch，防止旧回调在任务已取消或重开后误修改状态。没有回调能力的第三方可采用有退避的轮询，但要在 deadline 后交接或终止，不能无限占用资源。

## 6.5 衡量工具边界是否可靠

重点指标包括 schema 通过但业务前置条件失败的比例、重复副作用数、未知结果的对账时延、幂等键命中后的回执一致性、补偿完成率、第三方异步任务的孤儿率、资源冲突率和工具版本变更造成的 replay 差异。测试不应只覆盖成功调用；还应注入响应丢失、重复消息、乱序回调、权限在执行前撤销、资源版本变化和补偿再次失败。

本章的反例是纯只读、短时、无敏感数据的内部检索：为它实现完整 saga 可能得不偿失。反之，只要工具能够创建真实副作用，哪怕模型“几乎总是正确”，幂等、授权、回执和恢复都不应被省略。第七章将把这些真实回执送入验证和停止逻辑。
