# 第 1 章　为什么 Agent 是受约束的闭环系统，而不是“模型加工具”

## 1.1 从一次任务的第一秒开始理解 Agent

当采购负责人按下“开始调研”时，系统接收到的并不只是一个自然语言问题。它同时收到请求主体、所属租户、目的、候选供应商标识、可访问的数据域、时限、可花费的预算，以及组织已经声明的禁止动作。若系统把这些都拼进一段提示词，再让模型在 `while` 循环中自行决定下一步，表面上已经有了“模型加工具”的 Agent；但一旦模型误读范围、工具超时、用户撤销请求或服务重启，系统就无法回答四个基本问题：这次任务是否仍被授权、外部世界实际上发生了什么、下一步是否安全、最终交付是否真的满足请求。

因此，产业级 Agent 的最小定义不是“会调用工具的聊天模型”，而是一个在部分可观测环境中反复执行**观察—提出候选—门控—行动—验证—状态转移**的闭环控制系统。模型适合处理语义理解、从非结构化材料提取候选事实、提出检索和计划选项；运行时适合保存状态、等待事件、恢复执行；工具网关适合验证权限与参数、实施幂等和超时；验证层适合判定某项事实是否有来源、测试是否通过、业务对象是否真的改变。任何一层缺失，另一层都不能可靠替代它。

这一区分与 ReAct 的价值并不矛盾。ReAct 展示了将推理轨迹与行动交替，可以让语言模型依据环境观察修正后续动作；它提供的是一种生成候选行动的范式，而不是授权、恢复或事务协议。[ReAct](https://arxiv.org/abs/2210.03629) 因而，在本章案例中，模型可以建议“先查询制裁名单，再读取数据处理条款”；真正的系统仍要检查这两个读取是否属于本任务可访问的租户与目的，并把工具返回作为证据，而不是把模型的叙述当作世界状态。

## 1.2 用 O—R—A—L 分析闭环，而不是用它替代系统定义

O—R—A—L 可以作为检查 Agent 闭环的分析视角，但不是充分必要定义。**Observe** 不是把所有输入原样塞进上下文，而是从环境取得观测，校验来源、版本、权限和时效，并区分事实、回执与不可信内容。**Reason** 是在目标、验收条件、预算和禁止事项约束下形成候选解释、计划或动作。**Act** 只有经过策略、权限、参数和风险门控后才影响环境，动作结果还要重新进入 Observe。**Learn** 则是受治理的更新过程，不等同于在每轮生成中“自我反思”。

Learn 至少发生在四种不同时间尺度。运行内学习以新观测修正当前状态和计划，任务结束后即失效；跨任务记忆保存带来源、范围和期限的经验；策略资产更新 prompt、检索、路由、工具说明或工作流；参数层学习才会通过训练改变模型权重。影响范围越大，发布门、独立评测和回滚要求越严格。并非每个 Agent 都要在每一轮、每一层执行 Learn；一个只在当前 run 内重规划、从不写长期记忆的系统，仍可能形成完整而可靠的任务闭环。

这一视角也给出明确边界：Agent 研究不应等同于 LLM 研究。LLM 可以是 Reason 中的重要策略组件，也可以辅助 Observe 中的信息抽取或 Learn 中的候选归纳，但完整 Agent 还包含状态、记忆、行动空间、权限、工具、验证、事务、恢复和学习管道。只替换模型并不会自动修复重复副作用、越权访问、过期审批或崩溃后的状态丢失。

## 1.3 失败为什么会在闭环的接口处放大

最常见的错误做法是把成功理解为“模型说已经完成”。这会使供应商 A 的调研在没有读取最新政策、没有对合同版本做核验时就输出一份流畅的建议书。第二种错误是把所有非成功状态一律解释成“再试一次”：网页限流、权限被拒、合同库返回空结果、回调尚未到达和真实的业务失败被混为一谈，导致成本上升、循环加深甚至重复写入。第三种错误是把工具调用视为原子且可信：网络超时后重发一个写请求，可能已经造成两次提交；工具返回一段自由文本，也可能夹带提示注入或旧版本事实。

这些故障都来自反馈闭环没有被建模。控制系统需要区分三件事：模型的候选解释、工具的执行回执和外部业务对象的可观察状态。调研 Agent 调用“获取合同”成功，只说明服务端接受了读取请求；返回的合同是否属于正确供应商、版本是否仍有效、是否包含所需条款，仍要由结构化字段与验证规则判断。对于写操作，工具返回 `accepted` 更不能等同于业务效果已达成。把这三层压缩为一句“工具成功了”，会让后续计划建立在错误事实之上。

## 1.4 闭环的责任边界

一个可实施的设计原则是：**模型拥有提案权，不拥有提交权；业务系统拥有业务真相，运行时拥有执行真相，验证器拥有完成判定权。** 业务真相例如供应商当前准入状态、合同版本和审批人；执行真相例如本 run 已派发的动作、重试次数、等待中的异步任务；完成判定则来自任务契约规定的证据与规则。模型可以从这些材料中综合出解释，却不应覆盖它们。

在工程上，应把一个 run 看成有身份、版本和生命周期的对象，而不是某个 HTTP 请求的副作用。最小记录包括 `run_id`、`principal`、`tenant_id`、`task_contract_version`、`policy_version`、`risk_level`、`started_at`、`deadline`、`budget_remaining` 和 `terminal_state`。每个动作另有 `action_id`、父动作、候选来源、工具版本、参数哈希、幂等键、授权决定、回执引用和 trace 标识。它们让团队可以在事后重建“谁在何种权限下，为何执行了这一步”，也让运行时在重启后不必重新询问模型已经做过的选择。

这种分工不等于所有任务都要使用复杂 Agent。若供应商准入只需读取一张结构化表并按固定阈值判定，确定性 Workflow 更简单、可测且成本更低。Anthropic 对 workflow 与 agent 的工程区分亦强调：前者是预定义代码路径，后者才让模型动态决定过程与工具；应从最简单足够的形态开始。[Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) Agent 的价值在于路径未知但可以取得反馈，而不是在每个自动化场景中替代代码。

## 1.5 如何判断闭环是否真的成立

不要只统计模型回答是否“像人”。应测量：在业务窗口内达到验收谓词且无错误副作用的**有效成功率**；用户取消后系统停止或进入必要补偿的时间；工具超时后仍处于 `unknown` 的比例；每次成功任务的模型、工具和人工成本；以及能够以隔离环境重建关键 run 的比例。若供应商准入建议语言质量提高，但因无法解释证据、越过数据域或漏掉异步制裁筛查而使人工返工上升，它不是更好的闭环。

本章的边界也必须明确：闭环并不保证模型的事实判断正确，不能把校准分数当作法律结论，也不能因为系统能恢复就允许不可逆动作。它只提供一个可把不确定性约束、暴露、验证和止损的执行外壳。下一章的任务契约决定这个外壳究竟为谁、在什么范围内、以何种证据工作。
