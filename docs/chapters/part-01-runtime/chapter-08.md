# 第 8 章　人在回路与可恢复的多智能体协作：怎样交接、仲裁与收敛

## 8.1 先划清术语和责任边界

本章讨论的是团队拓扑已经选定以后，多个执行主体怎样在同一任务契约下协作、恢复和收敛；是否应该使用多智能体，由第 10 章判断。多智能体不是默认优于单 Agent。当任务无法独立验收、共享写入高度耦合或验证信号薄弱时，增加角色通常只会增加通信、同步和相关错误。即使团队成员给出一致结论，一致也不等于真值；它可能只是同一过期数据、同一提示或同一验证偏差被重复放大。

经典 Swarm Intelligence 与 LLM 多智能体编排也不是同义词。前者通常强调个体依据局部信息和简单交互形成可测的群体行为；后者往往有显式控制器、角色、依赖图、共享制品和集中式验证。本书正文主称“多智能体协作”或“多智能体编排”。只有系统确有去中心化局部交互，并以实验测出群体层面的涌现效应时，才称“群体智能”。实现对象可以为了兼容不同框架命名为 `TeamState` 或 `SwarmState`，但命名本身不证明系统具有群体智能。

协作系统有两条不可让渡的边界。第一，worker 只拥有提案权：它提交不可变、带版本的制品或变更建议，只有获授权的控制器、聚合器或确定性合并服务可以提交团队共享真相。第二，完成和取消都是团队级状态转移，不能由某个聊天消息中的“完成了”“停止吧”触发。团队 reducer 必须读取持久事件和可验证证据，才能改变团队状态。

## 8.2 把协作对象写成协议

多智能体协作不能依赖所有角色“记得约定”。以下对象共同构成可恢复协议，附录 C 给出字段字典。

### 8.2.1 Task Contract 与 Team Contract

`Task Contract` 规定请求主体、目标、范围、交付物、完成谓词、禁止副作用、证据、预算和终态。`Team Contract` 在不放宽任务契约的前提下，进一步规定团队成员、角色、责任边界、允许的交互、共享对象、验证和合并权、升级路径、停止规则以及团队预算。任何子 Agent 的能力都只能比父任务更窄：它可以少看数据、少用工具、少写路径，却不能通过委派获得父任务没有的权限或延长父任务的截止时间。

Team Contract 还应说明谁能创建和取消 `WorkUnit`，谁能续租，谁能接受 `Merge Proposal`，什么证据可以满足团队完成谓词，以及控制器故障时由谁接管。契约发生版本变化时，只影响尚未提交的工作；已经产生的制品保留原契约版本，必须经过重新验证才能进入新版本的共享状态。

### 8.2.2 WorkGraph 与 WorkUnit

`WorkGraph` 表示子目标及其依赖、汇合点和失效传播关系。只有分解严格呈父子层级时才使用 `WorkTree`；有交叉依赖、多个前置条件或局部重规划时，逻辑结构应称为 WorkGraph，而不能借用 Git worktree 来表达任务关系。

`WorkUnit` 是可派发、可独立验收的最小工作项。它至少需要唯一 ID、所属契约版本、输入快照、依赖、局部交付物、完成谓词、允许工具与数据域、预算、截止时间、风险、重试上限和升级策略。分解是否有效，不看角色名称是否丰富，而看每个 WorkUnit 能否在不改写其他成员状态的情况下生成可验证制品。

### 8.2.3 Team/Swarm State 与 WorkState

`TeamState` 或 `SwarmState` 保存团队当前契约、WorkGraph 版本、WorkUnit 索引、共享制品引用、未决冲突、预算、取消代次、完成谓词评估和控制器租约。它是团队执行真相的投影，不是所有聊天记录的拼接。

`WorkState` 是本手册为可恢复工作单元定义的状态对象，不声称是跨框架标准。推荐主生命周期为 `queued → leased → running → submitted → verifying → merged → done`，并保留 `blocked`、`retryable_failed`、`needs_replan`、`escalated`、`cancelled` 和 `expired` 等侧状态。状态转换由事件、前置条件和授权角色共同决定；worker 可以请求转换，却不能自行把 `submitted` 改成 `merged` 或 `done`。

### 8.2.4 Artifact 与 Message/Event

`Artifact` 是不可变、可寻址且带版本的协作产物，例如证据包、代码补丁、测试回执、计划差异或审阅意见。它应携带内容摘要、生成者、输入与契约版本、来源、适用范围和验证状态。共享状态保存 artifact 引用，不允许多个 worker 原地覆盖同一自由文本字段。

`Message` 用于传递建议或通知，`Event` 才是能驱动 reducer 的持久事实。消息被接收不代表动作已执行；“请取消”只有被授权入口转成带取消代次的事件后，才会改变 WorkState；“我已完成”只有连同制品、回执和验证结果进入事件流后，才可能满足完成谓词。事件要有唯一 ID、因果父事件、幂等键、生产者、契约版本和时间。

### 8.2.5 Lease、fencing token 与迟到结果

`Lease` 表示 worker 在有限时间内处理某个 WorkUnit 的权利，不表示它拥有共享结果。每次分配或重新分配都产生单调递增的 fencing token。写入检查点、提交制品和申请续租时必须携带 token；存储层或控制器拒绝小于当前 token 的写入，这样失联 worker 在租约过期后返回，也不能覆盖新 owner 的结果。

租约必须绑定明确的过期时间、心跳、最大续租次数和恢复策略。时间到达不等于 worker 一定失败，但意味着旧 token 失去提交资格。迟到结果可以作为诊断附件保留；只有重新验证且创建新的提案，它才可能被采用，绝不能靠到达顺序成为团队真相。

### 8.2.6 Merge Proposal、Conflict Case 与完成谓词

`Merge Proposal` 把候选制品、目标基线、变更摘要、前置条件、验证证据、风险、回滚方式和作者 token 绑定在一起。聚合器先检查契约与租约，再由独立 verifier 对当前目标状态验证；验证通过仍不必自动合并，高风险任务可以要求人工批准。

两个提案在事实、目标版本、资源写集或完成解释上不兼容时，系统创建 `Conflict Case`，记录冲突项、各方证据、受影响 WorkUnit、可自动采用的确定性规则和仲裁 owner。冲突不能由最后发言者、角色资历或简单多数投票消解。若没有预先批准的规则，就应暂停受影响子图并进入人工仲裁。

团队 reducer 根据事件产生 TeamState 和 WorkState；团队 completion predicate 则从任务契约、所有必要 WorkUnit、共享制品与独立回执计算是否完成。二者都应是可版本化、可重放的系统逻辑。控制器负责推进，而不能把自己生成的总结当作验证证据。

## 8.3 从准入到分解：先证明团队可以安全开始

协作运行首先经过准入。控制器读取 Task Contract，校验请求主体、资源范围、团队预算、截止时间、风险级别和必要的人类 owner；随后建立 Team Contract，并确认不存在通过委派扩大权限的路径。若目标含糊、完成谓词不可验证、共享写入没有仲裁者或故障后无人接管，正确结果是拒绝准入或请求补全，而不是先创建一组角色再观察结果。

通过准入后，规划器把目标分解为 WorkGraph。每个 WorkUnit 应产生一个可以独立检查的 artifact，显式声明输入快照和依赖。多个检索任务可以并行，但对同一业务记录的两个写请求应先收敛为一个提案；需要反方证据时，应在 reviewer 看到主结论前固定其输入和 rubric，减少跟随偏差。控制器还要预留验证、冲突处理、恢复和人工接管预算，不能把全部额度发给生成 worker。

分解结果本身要过一次检查：依赖图无等待环，所有叶节点有 owner 类型，所有汇合点有合并规则，失败能定位到受影响子图，取消可以从根向下传播，且团队完成谓词不会仅因全部 worker 自报完成而成立。检查通过后，TeamState 记录 WorkGraph 版本并发出可重放的派发事件。

## 8.4 派发、隔离和检查点

控制器只派发依赖已满足的 WorkUnit，并附带输入 artifact 版本、能力令牌、局部预算、deadline、lease 与 fencing token。worker 启动后先校验这些字段，再将状态从 `leased` 转为 `running`。如果输入版本已经过期或本地环境与要求不符，它应返回结构化阻塞事件，而不是基于猜测继续。

隔离至少包含状态、文件或资源写集、凭证和费用归属。不同 worker 不应共享一个可任意改写的对话历史，也不应持有共同的长期凭证。文件型任务可使用独立工作目录，代码任务可使用第 26 章所述 Git worktree；但隔离检出不等于安全沙箱，网络、缓存、端口、数据库和外部副作用仍要由容器、策略与能力网关限制。

长 WorkUnit 要在可验证边界写检查点。检查点包括输入版本、已完成步骤、文件或资源摘要、命令和工具回执、未决假设、预算消耗、lease token 以及下一个安全恢复点。worker 只追加 checkpoint/event，不直接改 TeamState。控制器用幂等键折叠重复事件，用 reducer 生成新投影；恢复者只能相信已持久化的制品和回执，不能假设失联进程内的上下文仍然存在。

## 8.5 提交、独立验证、合并与局部重规划

worker 完成局部工作后，将 WorkState 改为 `submitted`，提交不可变 artifact 或 Merge Proposal。提交不是集成，更不是团队完成。验证器必须在独立身份和尽可能独立的证据路径上检查 schema、来源、权限、目标基线、局部完成谓词、隐藏约束和副作用。为了降低相关偏差，关键结论不应只由使用同一模型、prompt、检索库和工具的另一个角色复述。

验证失败时，系统保留原提案和失败证据，并依据稳定错误分类行动。可修复且仍在预算内的局部错误进入 `retryable_failed`；输入前提失效进入 `needs_replan`；权限、范围或高风险冲突进入 `escalated`；过期 token 或已取消工作进入 `expired` 或 `cancelled`。重试必须获得新 lease 和新 token，且说明相较上次新增的证据、工具或假设；否则 reducer 拒绝同错重试。

验证通过后，只有授权聚合器或确定性合并服务能把提案合入当前目标状态。它在合并前再次检查目标版本和并发写集，合并后记录新 artifact 版本与外部回执，并将 WorkState 依次转为 `merged`、`done`。如果合并改变了其他节点的前提，控制器只重规划受影响子图，保留未受影响的已验证结果；全图从头执行会制造重复劳动，也会丢失可归因证据。

## 8.6 停止、取消、清理与经验候选

正常停止需要团队 completion predicate 在当前契约版本下为真，必要 artifact 已合并，外部副作用已验证，未决 Conflict Case 已解决，且没有必须运行的 WorkUnit 仍处于非终态。预算耗尽、deadline 到达、权限撤销或人工 kill 则产生不同终态；系统不能把“停止运行”统一写成成功。

取消从 TeamState 的取消代次开始，控制器停止新派发并向所有未终结 WorkUnit 写取消事件。worker 收到消息只是提示；它在持久状态中观察到更高取消代次后，才停止可中断动作、保存诊断、撤销短期凭证并报告补偿需求。对已经越过不可逆点的动作，取消只能阻止后续步骤并启动预先定义的补偿或人工处置，不能伪称世界已经恢复。

清理发生在制品、事件、诊断和审计引用已经保留之后。控制器回收 lease、凭证、临时工作区和外部资源，并为异常环境设置隔离期限。最后，系统可以从验证成功、失败恢复、冲突仲裁和人工修改中生成 `Learning Candidate`；候选必须携带来源、契约版本、归因不确定性和适用范围，进入第 15 章的发布门，不能直接写共享记忆或训练模型。

## 8.7 故障必须有检测信号、确定性响应和恢复边界

每种协作故障都应预先定义四件事：系统看见什么信号、立即执行什么确定性响应、从哪个持久边界恢复、何时交给人。下面的最小故障集不能只靠 prompt 提醒规避。

### 8.7.1 重复劳动与任务漂移

- 重复劳动可以由相同 WorkUnit 签名、重叠输入与写集、近似 artifact 摘要或重复成本增长检测。控制器应复用已有租约或已验证制品，取消多余副本；只有在契约明确要求独立复核时，才保留重复执行，并把它标记为独立证据任务。恢复边界是最近一次已接受的 artifact，而不是任一 worker 的最长文本。无法判断两个工作项是否等价时，handoff packet 应列出差异与继续两者的成本。
- 任务漂移表现为输出 scope、工具调用、文件路径或目标谓词偏离 WorkUnit/Team Contract。网关立即拒绝越界动作，控制器将该单元转为 `needs_replan` 或 `escalated`，并从原输入快照恢复。若继续需要扩大权限、目标或预算，必须由原授权主体修改契约，不能让子 Agent 自批。

### 8.7.2 矛盾制品与并发写

- 矛盾制品可由 claim ledger 中同一主张的相反状态、来源版本冲突或验证结果不一致发现。控制器创建 Conflict Case，冻结依赖这些主张的子图，并要求独立证据或确定性仲裁规则。恢复边界是冲突前最后一个共同验证版本；影响完成定义或高后果决策时必须人工仲裁。
- 并发写由相同资源写集、目标版本不一致、条件更新失败或合并冲突检测。系统拒绝后到或过期提案，重新读取权威状态，再决定重基、串行化或补偿。聊天中的“你先写”不是并发控制。自动合并无法证明语义兼容时，应把最小 diff、双方意图和测试结果交给 owner。

### 8.7.3 失联、租约过期与迟到回执

- worker 失联由心跳缺失、lease 即将过期和检查点无进展检测。控制器停止续租，吊销短期能力并从最后持久检查点重新分配；进程内未记录内容不属于恢复范围。连续失联或涉及未知外部副作用时，人工包必须包含最后确认的动作、幂等键和待对账对象。
- 过期 lease 和迟到回执通过 fencing token、事件代次与提交时间检测。存储层拒绝旧 token 改写状态，但保留回执供对账；若回执表明外部动作可能已经发生，系统先查询业务真相，再决定采纳、补偿或创建冲突，绝不盲目重试。无法查询或补偿的高后果动作立即交接。

### 8.7.4 无限重试、无限交接与等待环

- 无限重试或交接可由相同失败签名、owner 循环、无新增证据、重试次数和预算斜率检测。reducer 只允许有新信息或不同恢复策略的有限重试，超过阈值进入 `blocked` 或 `escalated`。恢复边界是首次稳定失败的 checkpoint；人类看到的是失败簇和已排除方案，而不是几十轮原始聊天。
- 等待环由 wait-for graph 中的环和超过 deadline 的依赖检测。控制器按照预先定义的优先级取消、降级或重排一个分支，并使受影响节点进入 `needs_replan`。若没有安全的断环规则，应由能够改变需求或提供缺失事实的人仲裁。

### 8.7.5 错误级联与虚假完成

- 错误级联表现为某个未验证 artifact 被多个下游节点消费、同一失败签名跨子图扩散或取消未传播。控制器按 provenance 反向标记受污染制品，使依赖子图失效并停止继续派发；已验证且不依赖该输入的分支可以保留。若影响已合并的外部结果，系统升级为事故并附带影响清单与补偿状态。
- 虚假完成由 worker 自报与 completion predicate、缺失回执、未决冲突或未终结依赖不一致检测。团队 reducer 拒绝进入 `done`，把缺口转为新的验证 WorkUnit。完成谓词本身有歧义、或证据只能由有利益关联的一方提供时，需要人确认验收定义。

### 8.7.6 权限越界、成本失控与相关验证偏差

- prompt injection 或权限越界由不可信内容中的指令、工具网关拒绝、scope/路径不匹配和能力升级请求检测。确定性响应是拒绝动作、隔离输入、吊销相关 token 并保留证据；恢复从注入内容进入前的可信 checkpoint 开始。若秘密可能泄露、外部副作用已发生或需要扩大权限，转安全/业务 owner 处理。
- 成本失控由预算消耗斜率、通信 token 占比、重复调用、并发数和预计完工成本检测。控制器降低并发、停止低价值分支、切换已批准的降级路径并保留验证预算；不得为了省钱跳过权限检查或最终验证。是否增加总预算只能由 Team Contract 指定的预算 owner 决定。
- 相关验证偏差表现为多个 verifier 共享相同模型、数据源、prompt 或错误工具，以及结论高度一致但独立来源比例下降。系统要求盲复核、不同证据路径或确定性检查，并把简单投票标为不足。高影响结论没有真正独立证据时，应交给领域专家。

### 8.7.7 控制器故障

- 控制器故障由 leader lease 过期、事件序号停滞、重复派发或 reducer 投影不一致检测。备用控制器只能在获得更高 fencing token 后接管，从事件日志重建 TeamState，并对未决外部动作先对账；两个控制器不能同时提交共享真相。事件日志损坏、完成谓词版本不明或外部副作用无法归属时，系统应冻结合并与新派发，生成全团队 handoff packet，由人决定恢复或终止。

## 8.8 人工接管是可恢复协议的一部分

人工介入应发生在系统无法合法或可靠推进的决策点：契约关键字段缺失、权限或预算需要扩大、不可逆动作待批准、独立证据冲突、未知副作用待对账、控制器无法安全恢复，或继续计算的预期价值为负但任务尚未满足。运行时保存检查点并进入 `escalated`，而不是保持一个模型连接等待。

handoff packet 是最小、可行动的状态投影。它至少包含任务与 Team Contract 版本、当前 TeamState、受影响 WorkUnit、已验证事实、Conflict Case、未知外部效果、最近安全检查点、租约与取消状态、预算和 deadline、已尝试方案、建议选项、每个选项的影响与可撤销性，以及 trace/artifact 引用。包还应明确“人需要决定什么”和决定的有效期；若合同、目标基线或权限已经变化，旧批准不得自动复用。

人的回复必须以身份明确、参数绑定、带版本的事件进入系统。控制器重新校验当前状态后才恢复相关子图。批准不是把后续全部步骤交给 Agent 的空白授权，拒绝也不等于整个团队一定失败；reducer 根据回复更新契约、取消分支、采用制品或进入补偿。

## 8.9 用团队指标判断协作是否值得

所有团队实验先保留强单 Agent 基线，并在相同任务分布、权限、验证器和预算口径下比较。核心结果指标是经验证成功率、错误完成率、单位安全验收任务成本和 P95 完成时间；平均分或“角色讨论很充分”不能代替任务结果。

协作开销至少包括通信 token 与等待延迟、重复 WorkUnit 率、合并冲突率、孤儿任务率、lease 过期和重新分配次数、取消传播完成率以及从故障到恢复的时间。证据质量还要报告独立证据比例、相关错误率和 Conflict Case 的人工仲裁比例。最终交付需记录人工接管率、理解 handoff packet 的时间、人工返工量和合并后回滚。

这些指标应按拓扑、任务难度、风险、工具和失败类型切片。若团队相对强单 Agent 只提高文本评分，却提高 P95、冲突和人工返工，协作没有创造可接受的净价值。反过来，某些团队即使总 token 更多，只要独立证据显著降低高后果错误、恢复更快，也可能是合理权衡。

## 8.10 本章边界

多智能体协议提供的是责任、恢复和收敛机制，不提供事实正确性的保证。它不能把群体一致变成真值，不能把独立角色名称变成独立证据，也不能让 Git worktree 变成权限边界。第 21 章说明团队状态如何服从通用持久化、幂等和重放语义；第 26 章把 WorkState 落到代码任务的 Git worktree 生命周期；第 15 章说明团队经验如何经过归因和发布门，而不是从最终成功直接进入训练。
