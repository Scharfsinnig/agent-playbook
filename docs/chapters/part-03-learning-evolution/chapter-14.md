# 第 14 章　从轨迹到经验：数据飞轮为何首先是一条治理流水线

## 14.1 生产轨迹是候选证据，不是训练数据

一次任务轨迹包含请求、身份、上下文版本、检索证据、模型候选、工具调用、观察、人工介入、终态、成本和时间。它对事故复盘极有价值，却不天然适合记忆或训练。生产日志可能含 PII、凭证、合同、第三方内容和用户未同意作训练的材料；也可能有未来信息泄漏、人工暗中修复、选择偏差、失败原因不明和同一模型自评成功。将这些数据无差别回流，会把隐私风险、错误行为和评测污染做成“持续学习”。

因此飞轮的入口应是候选区，而不是模型或向量库。轨迹进入后，先检查用途与合法基础、合同/地域限制、主体权利和保留期；再做最小化和脱敏；重放或查询最终环境状态，区分真实成功、人工修复后的成功、未验证、失败和被策略拒绝。随后对文档、任务模板、客户和时间做去重与切分，检测公开 benchmark、隐藏测试和教师提示泄漏。只有保留了来源、敏感级别、版本、验证证据、适用域和删除血缘的案例，才有资格被分流。

“失败归因”尤其不能被日志自动化神化。生产观测通常只能说明某个工具、检索或人工介入与结果相关；除非有随机化、干预设计、可信环境重放或满足明确假设的反事实方法，不能声称找到了因果根因。更稳妥的做法是记录最早可疑步骤、支持证据与归因置信度，再用最小修复实验或人工审查验证。这样的纪律避免把后验叙事训练成模型的确定信念。

## 14.2 经验要按用途分流，而非进入一个“大数据湖”

验证后的案例至少有四条不同去向。第一类进入回归、红队或动态挑战集，作为未来变更的独立传感器；这类案例不能无控制地同时用于优化与验收。第二类成为局部记忆候选，例如经用户确认的联系人偏好、带证据的项目事实或某一租户的恢复手册。第三类成为系统优化候选，用于 prompt、检索、工具描述、路由或工作流实验。第四类才是参数训练候选，可进一步标注为 SFT、偏好、蒸馏或 RL 环境数据。

同一轨迹的用途不同，所需标签也不同。SFT 需要在当时信息集下的正确行动；偏好数据需要成对候选和与业务结果相关的 rubric；单步 contextual bandit 至少需要状态、候选臂、所选动作、logging propensity、延迟/缺失 reward、行为策略及环境版本；记忆则需要来源、置信度、scope、TTL、冲突策略和用户可撤销性。多步离线 RL 还须逐决策记录 `(s_t, a_t, p_b(a_t|s_t), s_{t+1}, r_t, done)`、动作是否真实执行或被策略覆写，并处理轨迹级 support 与累积权重；单一终态 reward 不能代替这条时序记录。将它们都压成“问答对”会同时损失信用分配、权限边界和可删除性。

研究系统也在探索把 Agent 执行产生的轨迹同 RL 训练接口解耦，以便对不同框架的状态转移进行归因和优化；Agent Lightning 是其中一种实现路线。这种接口层解耦不会自动解决轨迹用途授权、奖励正确性或上线批准，因而不能绕过本章的候选区和发布门。[R45]({{ '/references/#r45' | relative_url }})

采购 Agent 的一条轨迹可具体说明这一分流。若系统在合同冲突时正确请求澄清，这一轨迹可进入时间外回归集；经审批确认的“项目 X 通知须抄送法务”可作为项目 scope 的长期记忆；多个失败案例显示模型误读交付期单位，可成为 prompt 或检索重排实验；只有在历史工具和环境版本均可重放、轨迹中没有未来信息且最终回执可证实的情况下，才可成为 SFT 的工具调用样本。若发生过越权项目查询，它更应进入红队和策略测试，而不是被当作“负例”随意混入生成训练。

## 14.3 自生成数据与数据退化的边界

合成数据可以扩展稀缺边界案例、生成格式扰动、为小模型提供教师轨迹，或在有 verifier 的环境中产生更多可验证解答。风险不在“合成”二字，而在题目、答案、评分和发布都由同一分布控制。若同一模型生成题、作答、评价并决定采纳，它可能围绕自己易通过的模式收缩，错误会代际放大。不存在跨领域通用的“合成比例上限”；合成比例、抽样权重和课程速度必须由独立外部锚点、时间外测试、真实/专家数据覆盖和安全回归决定。

最低要求是给每个样本标明人类、教师、程序生成、环境生成或混合来源；对可验证任务使用独立执行器或隐藏测试；让至少一端（题、答、judge/verifier）独立于待训练策略；保留难例、拒绝、修复和失败轨迹；监控多样性、事实错误的代际变化、教师—学生错误相关性和外部任务退化。没有外部锚点时，自举只可作为研究探索，不能直接支撑生产自治。

## 14.4 数据飞轮的指标和发布门

数据飞轮应同时测数据质量和业务因果，不应只测样本量。数据层需要看授权/用途覆盖、PII 或秘密残留、近重复率、验证覆盖、代表性、长尾覆盖、删除传播和来源完整度。学习层需要看各候选改动在冻结集、时间外集、旧能力集、安全集的增益与置信区间。上线层需要看 shadow 差异、canary 的增量任务成功、人工返工、投诉、成本、时延和回滚事件。A/B 或其他实验设计才能较可信地估计业务增量；上线前后的均值对比通常受用户与流量选择偏差影响。

发布门应分离训练反馈、开发选择、上线验收和审计。训练可见的 verifier 不应是唯一门禁；至少保留隐藏测试、不同版本的评分器或人工抽检。Shadow 在真实输入上执行候选但不产生副作用，能暴露分布漂移，却不能充分暴露真实写入竞态、用户反应和第三方故障；故 canary 仍需小 blast radius、预注册停止条件、分群下界和一键回滚。任何硬约束违规都不是“以平均指标补偿”的问题，而是冻结候选、调查证据和修正控制面的原因。

## 14.5 用数据契约防止“飞轮”变成无法删除的黑箱

数据契约应把每条轨迹的治理状态显式化，而不是靠团队记忆。一个候选记录可包含 `event_id`、主体/租户 scope、用途许可、采集时间、保留期、输入来源、敏感级别、模型/prompt/adapter/router/工具/环境版本、候选动作、观察、最终验证器和人审结论、人工介入、数据质量分级、训练/评测隔离标签、删除关联与血缘父节点。训练数据集则引用这些不可变记录，而不是复制出一个与源头脱节的 CSV。任何撤回、纠错、合同到期或工具 schema 废弃，都能沿血缘找到受影响的记忆、索引、评测、adapter 和发布版本。

数据契约还帮助区分“能用于训练”与“应当用于训练”。一条含客户秘密但可脱敏的成功轨迹，可能适合改进本租户的回归集，却不适合跨客户蒸馏；一条人工补救特别有价值的事故轨迹，可能适合作为红队而不适合作为直接模仿目标。数据 owner、风险 owner 和模型 owner 的签字也不应互相替代：前者确认来源与用途，后者确认风险阈值，训练负责人确认技术可复现性。没有这三种责任，飞轮会在事故后陷入“谁允许了它进入训练”的空白。

数据集进入训练前还应冻结一个 manifest：样本 ID 清单、抽样规则、去重阈值、过滤器版本、标签/验证器版本、切分规则和已知局限。训练结束后，把该 manifest 与模型制品关联。这样当发现某批合同解析样本含未来回执，团队能准确重跑受影响实验、判断盲测是否失效，并暂停相关模型，而不是只能删除原始日志后失去复盘线索。
