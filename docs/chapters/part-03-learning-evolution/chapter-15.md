# 第 15 章　多时间尺度学习：一次失败不应直接改写全局模型

## 15.1 四层资产，四种速度

持续进化不是单一训练作业，而是对不同可学习资产采用不同速度和可逆性。第一层是单次轨迹内的状态与策略适应：工具返回错误后重规划、缩短检索、请求澄清或停止。第二层是跨会话非参数资产：带来源的记忆、案例、技能和失败签名。第三层是策略制品：prompt、few-shot、检索参数、router、工具说明与工作流图。第四层才是参数权重：SFT、PEFT、偏好优化、蒸馏、RL 或持续预训练。越接近权重，影响范围越广、删除越难、回归要求越高。

把“采购合同版本冲突”放入这四层即可看出区别。在单轨迹内，Agent 应读取版本、提出澄清或切换到草稿，而不学习任何长期规则。若某项目负责人确认了稳定偏好，可保存为用户或项目 scope 的可删记忆。若大量已验证案例表明合同版本筛选缺少某字段，可更新检索过滤或工具说明，经过离线评测和 canary 发布。只有当各种上下文和工具修复后，模型仍反复不能将条款冲突表述为正确澄清问题，且有大量去重示范时，才考虑让这类行为进入 SFT/LoRA。

## 15.2 单轨迹反思：是受证据约束的重规划，不是自我训练

单轨迹反思发生在运行时状态中。验证器提供明确错误，例如“审批令牌与合同版本不匹配”；运行时保存当前状态、失败代码、已执行动作、预算和可用恢复动作；模型根据这些事实提出下一候选。反思的输出应该是计划差异或状态转移，如“撤销草稿、查询生效版本、请求新审批”，而不是把一段自由文本当作永久知识。Reflexion 等研究展示语言反馈可辅助后续尝试，但在企业任务中，反思若不绑定环境证据，常只是事后合理化。[Shinn et al., Reflexion](https://arxiv.org/abs/2303.11366)

运行时应限制反思的写入范围、次数、预算和权限。每次重试要有新信息、不同工具、不同假设或用户输入；若没有进展，应停止、降级或交接。记录的指标包括重复失败率、无进展循环率、平均恢复步数、恢复后真实成功、错误完成率和额外成本。反例是让模型不断总结“下次更仔细”，再把这些总结写入共享记忆；这既没有验证因果，也会让偶然或被注入的文本跨会话传播。

## 15.3 跨会话记忆：局部、可撤销、可证明

跨会话记忆解决的是状态窗口之外的连续性，而不是训练模型权重。可保存的对象包括用户已确认的偏好、来源明确的事实、成功的受限工具模板、失败签名和经验证的恢复手册。每条记忆应有 namespace（用户/组织/项目）、来源事件、时间、置信度、适用条件、TTL、敏感级别、读写 ACL、冲突关系和删除路径。当前用户明确指令始终高于历史偏好；外部网页或模型猜测不应拥有写入权。

局部记忆可以在会话后异步写入，但需满足“用户确认或可验证、带 provenance、影响范围受限、可立即撤销”。影响跨用户行为的记忆 schema、提取器、召回排序或共享技能则不再是局部记忆，而是系统策略制品，应走离线回归、shadow 和 canary。LangGraph 的持久化设计也将线程内 checkpoint 与跨线程 store 分开：前者服务恢复和短期状态，后者才存放可跨会话访问的数据。[LangGraph persistence](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/persistence.mdx)

## 15.4 Prompt、检索和路由优化：把系统配置当作代码发布

策略层学习的优点是修改可见、可版本化且比权重更容易回退。可从失败簇提出候选：调整 prompt 中的澄清顺序、改善检索 query rewrite、为工具增加负例描述、改 router 的升级阈值、或修改工作流的重试分类。每项候选必须在开发集内产生，在独立时间外集、旧能力与安全集上选择；不要用同一案例既生成优化又证明成功。发布时记录制品 digest、实验桶、流量范围、终止条件和回滚版本。

策略优化还应维持一个对照版本，而不是连续在同一在线策略上叠加改动。若本周改了 prompt、下周换了 reranker、随后又调路由阈值，任何线上提升都无法归因。更稳妥的节奏是一次实验只改变可解释的少数制品，保留基线、候选和失败样本；对存在交互效应的改动再做组合实验。发生退化时，先按 release manifest 回到已知良好组合，再从 trace 找到最小差异。这样既避免“在线自我改写”的不可控累积，也能让成功经验被证据支持后进入下一层。

这层也存在奖励投机。例如只把“工具调用成功”当 router reward，会让路由选择容易返回 200 的工具，而非真正完成采购变更；只优化 prompt 的文本评分，会牺牲拒绝和成本。因此系统优化应以环境有效完成、轨迹合规和护栏为主目标。可以使用离线搜索、贝叶斯优化、A/B 或受控 Bandit，但不能让生产模型根据自己对一次回答的满意度立即改写全局 prompt。

## 15.5 团队经验：先进入候选区，再通过发布门

多智能体协作会产生比单轨迹更复杂的经验来源：WorkUnit 的输入和输出、版本化 artifact、验证器的接受或否决、Merge Proposal 与 Conflict Case、租约过期后的恢复、人工仲裁的修改，以及合并后的真实结果。它们应先按 task、WorkGraph、契约和制品版本建立 provenance，再生成团队经验候选。聊天中谁最后总结，不是经验来源；最终任务成功也不能证明此前每个局部动作都正确。

贡献归因通常具有不确定性。某个检索 worker 提供了关键证据，critic 排除了错误解释，控制器取消了高风险分支，维护者又修改了最终补丁，成功可能来自这些因素的组合。系统应记录候选贡献链、反证、被覆盖的提案、验证独立性和人工改动，并把归因置信度与备选解释一起保存。除非有可识别的干预或受控实验，否则不能把时间上靠近结果的行为写成因果标签，尤其不能把最终成功自动归功于最后一个 Agent。

团队经验首先进入隔离的候选区。候选区拒绝未经验证的自报完成、过期 lease 的输出、来源不明的消息、被 prompt injection 污染的内容和无法说明数据用途的轨迹；它还要去重，检查跨租户数据、许可、敏感信息、评测集污染和贡献争议。候选可以用于提出局部记忆、失败签名、工作流规则、评测样本或训练示范，但尚未成为任何在线资产。

发布门依据影响尺度逐级收紧。局部可删记忆需要来源、scope、TTL 和冲突检查；共享技能、prompt、路由或 WorkGraph 模板需要独立离线回归、shadow/canary、预算与安全门；参数数据还需要数据治理、去重、归因审阅、旧能力回归和模型发布批准。任何团队轨迹都不得因“最终成功”直接写入共享记忆或直接训练，生产 worker 也不应拥有绕过候选区和发布门的权限。

## 15.6 参数更新：最慢的通道，最高的证据门槛

权重更新前需要一个可复现的“能力缺口说明书”：问题在哪些任务/客户/时间切片重现；对契约、RAG、工具、状态和 prompt 的最小修复实验结果；训练数据来源与用途；基线、训练设置和预期收益；受保护的旧能力；安全威胁与发布回退计划。训练完成后，模型/adapter registry 应保存基座、量化配置、tokenizer、训练代码 hash、数据清单、超参、随机种子、评测报告、风险接受人和撤销版本。

这不是文档负担，而是可归因的前提。没有这些信息，当 canary 显示采购 Agent 的通知质量提高但法语项目的拒绝率下降时，团队无法判断是数据、adapter、router、索引还是 prompt 变化造成，也无法安全恢复。参数更新的生产流程应是隔离训练、独立评测、shadow、分群 canary、逐步扩量和持续监测，而不是训练 job 完成后自动替换线上模型。

多时间尺度并不意味着每层都“自动”。S0 的恢复行动只能在当前任务的权限和预算内发生；S1 的局部记忆写入须可撤销；S2 的配置优化必须由独立评测选择；S3 的权重更新还要受模型注册和批准约束。任何层若触及跨租户数据、全局行为或不可逆动作，就应上调到更慢、更严格的发布通道。这样，系统既能在一次合同冲突中迅速改走澄清路径，也不会因一次异常邮件把全局模型训练成错误偏好。
