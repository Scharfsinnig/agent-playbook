# 第 19 章　Agent 评测体系：评的不是一句话，而是一次受控任务

## 19.1 从“答案好不好”回到任务是否真正完成

传统文本评测常把输入交给模型，再把最后一段文字同参考答案比较。它适合概括、改写等没有外部副作用的任务，却不能回答 Agent 是否选择了不该选的工具、是否用错了客户身份、是否在失败后重复提交，也无法区分“订单正确创建”与“模型声称订单已创建”。生产评测的最小对象应当是一份任务契约：输入、初始业务状态、允许的工具与权限、完成谓词、禁止行动、预算、可接受的终态及证据。由此，评测对象从一段输出扩展为结果、单步、轨迹和后果的组合。

评测基础设施还要把任务定义同一次实际试跑分开。可将 task 视为可重复的任务/环境定义，将 trial 视为某版本 Agent 在该任务上的一次运行；grader 只消费规定的可观察证据，transcript 保存完整交互与工具轨迹，outcome 是面向业务的结果，harness 则负责搭建隔离环境、注入故障并收集这些制品。这些边界让同一任务可以跨模型、提示、工具或策略版本比较，同时减少评测程序、Agent 和被测环境相互污染。[R10]({{ '/references/#r10' | relative_url }})

结果评测问的是交付物或业务状态是否满足契约。例如研究报告的每一项关键结论能否被来源支持，客服改签是否落在用户确认的航段，代码修改后的测试是否真实通过。单步评测关注模型在一个决策点是否选择了恰当工具、参数和升级路径；它能快速定位“读到了正确资料却调用了发信工具”一类问题。轨迹评测进一步检查从开始到终态的序列：是否在审批前写入、是否绕过了租户过滤、是否多走了昂贵而无意义的循环。最终答案正确并不能豁免轨迹不合规，因为危险的路径可能已经产生了不可逆副作用。

因此，离线评测应把案例保存为可版本化的环境快照，而不是一组问答。每一例至少有 `case_id`、风险等级、输入、初始状态、工具 schema 与模拟返回、检索语料版本、期望状态、禁止动作、允许的等价路径、评分规则和有效期。对有多条合理路线的任务，不应用“精确工具序列”误伤候选版本；可以断言必须调用的工具集合、不得调用的工具集合、参数约束、关键状态顺序与最大副作用范围。LangSmith 的评测资料也把最终回答、单步和轨迹分开，并区分离线回归与线上监测；这里借用的是问题分类，而不是平台默认配置。[R52]({{ '/references/#r52' | relative_url }})

公开基准适合暴露不同能力切面：AgentBench 跨多种交互环境，[R46]({{ '/references/#r46' | relative_url }}) GAIA 强调现实问题中的推理与工具使用，[R47]({{ '/references/#r47' | relative_url }}) WebArena 提供可复现的网站任务，[R48]({{ '/references/#r48' | relative_url }}) OSWorld 覆盖多模态桌面操作，[R49]({{ '/references/#r49' | relative_url }}) τ-bench 则关注工具、用户和策略约束之间的交互。[R50]({{ '/references/#r50' | relative_url }}) 它们可以补充能力画像，却都不能代替本组织的权限、副作用和真实业务终态验收。

## 19.2 评分器必须与失败后果相称

能够由程序验证的内容，不应交给语言模型裁判。JSON Schema、金额阈值、工具参数、ACL、审批状态、引用是否存在、数据库断言、文件校验和、测试结果和状态机转换都应由确定性验证器判断。这样既便宜，也能把安全硬约束同“表达是否自然”清晰隔开。对于真实性、完整性、解释质量等没有唯一标准答案的项目，专家标注、成对比较和 LLM-as-a-judge 可以补充，但它们必须有可复核的 rubric，并在独立的人标保留集上检查一致性、位置偏差、长度偏差和重复运行方差。

LLM judge 的正确位置是质量传感器而非安全放行器。若 judge 认为回答“看起来有帮助”，这只能触发抽检、排名或离线分析；它不能允许付款、解除数据访问，也不能证明某个事实是真的。Google 的 Agent 评测资料把工具使用、多轮轨迹、任务成功、grounding、hallucination 和安全拆为不同指标，并允许组合程序评分与 judge；单一总分会掩盖系统层失败。[R53]({{ '/references/#r53' | relative_url }})

数据集也要与系统一起演化。最初可用二十到五十个由领域专家挑选的核心、拒绝和故障案例建立基线；随后把经审核的线上失败、投诉、人工接管、供应商故障和红队发现加入候选集。训练、提示词优化与路由调参所见的数据必须同时间外盲测和红队集分离。合成案例能补足极端场景，却常与生成它的模型同质，不能替代真实分布。更重要的是，日志只给出相关线索：一次用户未投诉可能是系统正确，也可能是用户没发现错误，不能直接当训练奖励或因果标签。

## 19.3 发布前后的两条反馈链

发布前采用由近到远的证据链。先测试策略、schema、解析器、幂等和状态 reducer；再测试检索、单个工具与单个决策；随后在冻结案例上运行结果与轨迹回归；最后进行故障注入、提示注入、历史 trace replay、shadow 和有限 canary。每一阶段都定义阈值、owner、最大暴露和回退条件。P0 类不变量，例如未授权外发、跨租户读取、未批准高后果动作，不应以“平均 99%”表述；在发布集和攻击集中应为零容忍。一般质量指标则要报告切片和置信区间，而不是只报告总体均值。

发布后没有标准答案，在线评测的任务变成尽早发现静默退化。低成本规则可检查格式、引用、审批和业务状态；抽样 judge 与人审可看语义问题；业务漏斗、返工、投诉、取消、补偿和人工接管反映真实后果。每一类线上失败都应通过 trace 链接到具体版本和状态，再经脱敏、合法基础与用途审查后回流离线集。Shadow 只能说明候选在记录的世界中会如何选择，不能暴露真实写入、并发冲突或用户反应；因此有副作用的能力仍须依赖隔离模拟器、幂等、审批和小 blast radius。

评测的边界同样重要。公开 benchmark 可以用于能力发现，却不能证明具体任务适用性：题目可能被训练数据污染，工具环境可能已失效，成功标准也未必包含隐私、时效和业务责任。SWE-bench Verified 后续暴露出的污染、坏题与可验证性问题说明，即使广泛使用的基准也需要持续审查其有效性。[R51]({{ '/references/#r51' | relative_url }}) 对外部世界强依赖的任务，回放只能近似复现当时观察，不能制造今天仍然存在的库存或网页。此时应把“不可重放”本身记录为风险，并提高人工复核或降低自治等级。
