# 第 23 章　组织、合规与责任：把治理做成系统接口

## 23.1 责任要能落到一次 run

业务 owner 决定用途、可接受错误、人工接管与成功指标；产品/工程 owner 维护任务契约、评测、发布和回滚；平台/SRE owner 维护身份、隔离、SLO、成本和灾备；安全 owner 维护威胁模型、策略、红队与响应；隐私/法务 owner 判断适用性、数据处理、合同、披露和留存；审批者只对绑定的范围和证据作决定。供应商提供模型并不会接过部署者对业务后果的责任。把这些角色写在 RACI 里还不够，系统还须将 owner、版本、批准、豁免、on-call 与到期日写入用例台账和 trace。

NIST AI RMF 的 GOVERN、MAP、MEASURE、MANAGE 可作为组织化框架：先建立问责、角色和政策，再识别使用情境、受影响人、数据与风险，随后以评测和监测测量，最后排序和处置风险。其 GenAI Profile 是跨领域的管理资源，不是强制认证，也不会替代具体法规。[R57]({{ '/references/#r57' | relative_url }})

发布证据包应回答：为什么做、谁受影响、哪些数据与工具、风险分级与不自动化的边界、评测/红队结果、模型和供应链清单、身份与审批策略、trace/replay 覆盖、SLO/预算、回退/停止演练、剩余风险与豁免。风险接受不是一次签字；模型、索引、工具、用途、地域、供应商条款或事故发生变化时，都应触发再评估。

## 23.2 法规是工程输入，不是标签

以下仅说明截至 2026-08-19 应进入工程门禁的时间敏感信息，不判断任何具体系统是否合规。欧盟 AI Act 的适用不能从“它是 Agent”推断，而要看是否进入欧盟市场或在欧盟使用、主体是 provider/deployer 等何种角色、预期用途、是否落入禁止实践、高风险系统或 GPAI 义务。GPAI 模型提供者的义务原则上自 2025-08-02 适用，但在该日前已经投放市场的 GPAI 模型可依过渡条款在 2027-08-02 前完成合规。Article 50 的透明度义务要按具体条款和主体核对；其中，在 2026-08-02 前已经投放市场、生成合成音频、图像、视频或文本的系统，其 Article 50(2) 机器可读标记义务过渡至 2026-12-02。AI Omnibus 于 2026-07-27 生效后，Article 6(2) 与 Annex III 高风险系统的实质规则自 2027-12-02 适用，Article 6(1) 与 Annex I 产品内嵌系统则自 2028-08-02 适用。Omnibus 新增的、针对非自愿亲密内容及儿童性虐待材料生成或操纵的禁止实践也自 2026-12-02 适用；因此不能把全部禁止实践一概归入 2025-02-02，也不能把“2026 年所有高风险义务都已生效”作为上线判断。应核对当前合并法律文本、具体角色、例外和适用领域的法律。[R58]({{ '/references/#r58' | relative_url }})

中国场景也不能把内部工具与面向公众的服务混为一谈。向中国境内公众提供生成式 AI 服务时，应按《生成式人工智能服务管理暂行办法》评估；未向境内公众提供服务的研发和内部应用并不当然适用该办法。具有舆论属性或社会动员能力的服务还涉及安全评估及算法备案、变更、注销。2025-09-01 起施行的生成合成内容标识规则，按服务提供者、内容传播服务和应用分发平台等不同角色，分别规定显式标识、文件元数据中的隐式标识、下载/复制/导出保持与传播核验；这些要求并非对每个角色、每类内容同时适用，也不能简化为“所有内部 Agent 都要水印”。尤其是第九条允许用户申请不含显式标识内容的例外路径时，服务提供者须先在用户协议中明确用户的标识义务和使用责任，并依法留存提供对象信息等相关日志不少于六个月；这是一项有特定触发条件的要求，不应泛化成普通内部 Agent 的统一日志规则。[R59]({{ '/references/#r59' | relative_url }})

数据治理也不应把“同意”当万能或唯一的答案。轨迹进入长期记忆、评测或训练前，要确定用途、适用的处理合法基础、告知/同意（如适用）、数据主体权利、合同限制、数据地域与保留/删除机制；取得同意本身不自动允许训练、跨境或无限保留。工程上应把这些结论转化为字段级数据分类、访问策略、TTL、用途绑定、导出/删除血缘和审计，而不是停在隐私政策文本里。

## 23.3 可执行 RACI 必须能响应一条异常 run

RACI 的粒度应落到用例和事件。业务 owner 对预期用途、受影响人、成功定义、可接受损失和自治范围负责；产品/工程 owner 对任务契约、流程、评测和交付负责；平台/SRE owner 对身份委托、状态、SLO、预算、灾备和停止能力负责；安全 owner 对威胁模型、策略、红队、漏洞和遏制负责；隐私/法务 owner 对适用性、处理基础、合同、地域、披露和留存结论负责；审批者只对绑定对象、参数、额度和有效期的一次动作负责。供应商或外包方可以提供能力，却不能成为“出了问题找不到 owner”的替代品。附录 B.2 与 B.3 给出全书 A0—A5 的统一口径和活动级 RACI 最小模板，避免不同案例把同一等级或同一签字理解成不同责任。

创建用例、提升写权限、增加数据类别、开通记忆写入、接入新工具、更换模型区域或发生重大事故，都应触发对应角色复审。高风险 trace 保存当前业务 owner、on-call、策略版本、审批人和豁免 ID；审批界面允许拒绝、转交或要求补证，不能让一次批准被后续模型输出复用。治理有效性须通过演练检验：供应商区域故障同时出现异常 egress 时，平台能否先执行 K2/K3，安全能否取到证据，业务能否转人工，法务/隐私能否依据事实包升级判断，工程能否回滚完整 manifest。演练中的决策耗时、错误操作和证据缺口本身就是治理指标。

## 23.4 台账与变更要连成可追溯血缘

用例台账保存目的、owner、自治等级、用户/地域、数据类别、外部系统、最高后果动作、批准范围和复审日期；制品台账保存模型、adapter、prompt、工作流、工具、MCP server、容器、依赖、索引、评测集、策略和路由器的来源、digest、许可、地区、测试证据、限制与撤销开关；供应商台账补充训练/保留选项、分包商、SLA、通知、删除、导出和退出条款。版本 manifest 与 trace 将三者相连：一次异常输出能反查其模型、prompt、工具、语料和批准；一个 CVE 或供应商条款变化也能反查受影响用例。

变更按风险而非文件扩展名管理。提示词热改可能改变权限理解，embedding 更新会改变检索与 ACL 边界，工具 schema 的可选字段可能开放新能力。变更单应含影响分析、候选 digest、离线/红队结果、兼容性、迁移、canary、回滚、owner 与批准。低风险文案可走快速路径但仍需版本和观测；涉及敏感数据、写工具、身份、模型区域、记忆或策略必须提高门禁。NIST SSDF 可作为将第三方组件、漏洞响应和安全要求嵌入交付流程的共同语言，而非另起一套孤立 AI 流程。[R55]({{ '/references/#r55' | relative_url }})

## 23.5 数据、地区、豁免和下线的工程化结果

法务/隐私结论需要转换成可执行配置：允许的处理目的、模型/服务地区、最小化和脱敏要求、告知或内容标识、TTL、删除触发器、访问限制、人类监督与证据留存。策略引擎据此过滤路由和工具，数据管道据此决定 trace 能否进入评测仓，存储层据此设置 residency、加密和删除血缘。结论不清时，应选择较窄区域、只读模式或人工处理。中国和欧盟等规则依服务对象、角色和预期用途而变，工程团队提供可复现的数据流、功能、用户、地域和控制事实包，而不是宣布“自动合规”。

豁免要写清缺口、范围、补偿控制、最大暴露、风险接受者、失效日和撤销条件；它不能覆盖法律禁止、未授权访问或最小停止能力缺失。到期未续即自动降级或停用。退出/下线从选供应商时开始：停止新流量与异步唤醒，冻结学习写入，撤销凭证和外发能力，对未完成事务对账/补偿，再按策略归档或删除数据、索引、缓存、记忆与审计副本。演练须证明旧 token 无法调用、删除内容不能召回、孤儿 worker 不会重启待办任务，并且 trace/dataset 可以导出以支持迁移。
